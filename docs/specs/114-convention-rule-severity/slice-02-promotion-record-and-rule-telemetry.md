## Slice 114-02 — promotion-record-and-rule-telemetry

**Goal:** Promoting or demoting a rule is an auditable record, malformed rule
blocks cannot land, and `gate-stats` shows per-rule fire counts beside bypass
counts so a keep/retire decision can be made from data.

**DoR:**
- ✅ 114-01 DONE (tagged rule shape + parser + verdict ids exist).
- ✅ Confirmed the lightweight-decisions entry shape (`decisions.py`) and the
  `gate-stats` digest columns, so the promotion record and the telemetry column
  reuse them rather than add a store.

**Acceptance Criteria:**

1. **Rule-block lint.** A check (wired into `scripts/ci_check.py` and the CI
   workflow beside `spec_lint.py`) fails on a rule block missing id/severity/
   state, a duplicate id, or an unknown enum value, naming the section and id.
   Observable: fixtures for each failure; the live `docs/conventions.md` and
   template pass.
2. **Promotion record.** A state change on a rule is recorded as a
   lightweight-decision entry naming the rule id, old→new state, and the
   reason; the lint warns when a state differs from the last recorded state
   for that id (a silent promotion). Observable: fixture with an unrecorded
   promotion produces the warning; a recorded one is silent.
3. **Per-rule fire counts.** `workflow.py gate-stats` gains a rules section:
   for each rule id, the count of review verdicts citing it in the window, next
   to the existing bypass counts, sourced from the recorded verdict artifacts
   (no new emit surface). Observable: digest output on a fixture repo with two
   verdicts citing one id shows `2` for that id and `0` for an uncited one.
4. **Denominator entry resolved or narrowed.** The refinement-todo entry
   "gate-bypass digest denominator" is updated: resolved for convention rules,
   with the remaining hook-gate half left deferred with its trigger intact.

**Anti-horizontal-phasing check:** After this slice a maintainer can answer
"is this rule dead weight or golden?" from the digest, and cannot promote a
rule to blocking without a record saying why.

### For `kind: spike` slices

When the slice's frontmatter has `kind: spike`, the body carries four
extra labelled blocks alongside the standard Goal / DoR / AC / DoD
scaffolding. Spike slices are timeboxed investigation, not feature
work — they reduce an unknown before committing to a design.

```markdown
**Question:** _One sentence stating the open question. Set at DRAFT._

**Time-box:** _Explicit budget — e.g., "1 day", "4 hours". Set at DRAFT._

**Findings:** _Bullet evidence collected during the spike. Filled
during IN_PROGRESS._

**Outcome:** _One of: `ADR-NNNN created` / `spec NNN-NN unblocked` /
`abandoned (reason)`. Multiple outcomes separated by `;`
(e.g., `ADR-0007 created; spec 030-02 unblocked`). Set at DONE._
```

`spec_lint.py` validates the `kind:` enum (allowed values: `spike`,
`feature`) and soft-warns when a `kind: spike` slice is missing any of
the four labels. Mid-flight spikes legitimately have empty Findings /
Outcome, so this is a warning, not a hard error.

See `skills/spec-workflow/SKILL.md` (Spike slices subsection) and
`docs/spec-workflow/spidr-primer.md` for the always-nested rule (spike
slices live inside a real spec, never as standalone `docs/spikes/`
artifacts) and the abandoned-outcome manual-reshape failure mode.
