## Slice 122-03 — one-blocking-rule

**Goal:** the reviewer prompt and every live doc state the blocking rule the
gate enforces: a pass clears only on `verdict: pass`, and a craft, arch or
code-health review with only nits and strengths is recorded as `pass`.

**Decision:** spec 122 D1 — conform the prose to
[ADR-0014](../../decisions/adr-0014-review-evidence-model.md) §3 (gate rule +
authoring rule); `verdict_clears` does not change.

**DoR:**
- ✅ ADR-0014 §3: "a nits-only craft review is recorded as `pass`"; gate clears
  iff `verdict: pass`.
- ✅ The contradicting prose is enumerated:
  `skills/spec-workflow/SKILL.md` (block rule for REVIEWED),
  `skills/independent-review/SKILL.md` (craft + arch paragraphs),
  `docs/workflow.md` (craft pass in "Post-implementation review").
  `review.py`'s shared craft/arch/code-health output format
  (`_PR_REVIEW_OUTPUT_FORMAT`) states no verdict rule at all.

**Assumptions:** None.

**Acceptance Criteria:**

1. **The prompt carries the authoring rule.** The output format shared by the
   craft, arch and code-health prompts says: `pass` when no `[blocker]` entry
   remains (nits and strengths go in `RECONCILIATION NOTES`); `needs-changes` or
   `fail` when at least one entry is `[blocker]`.
2. **spec-workflow states one rule.** The REVIEWED block rule says every
   required pass must record `verdict: pass`; a craft/arch/code-health review
   with only `[nit]`/`[strength]` entries returns `pass` and its nits go to the
   deviation log; a `needs-changes` from any pass blocks; and the orchestrator
   records the verdict the reviewer returned (never re-records a
   `needs-changes` as `pass` itself).
3. **The other live docs agree.** `independent-review/SKILL.md` and
   `docs/workflow.md` say the same. No live doc says a `needs-changes` "does not
   block" or becomes reconciliation-log items.
4. **The gate is unchanged.** `verdict_clears` and its tests are unchanged in
   behaviour.
5. **A test pins the agreement.** A test fails if a live doc paragraph pairs
   `needs-changes` with "does NOT block" / "reconciliation-log items", or if the
   shared output format loses the authoring rule.

**Edge cases to cover explicitly:**
- Closed records (spec 031 slices, ADR-0014's Context section) keep their
  historical wording — they are records, not live prose (ADR-0010); the pinning
  test does not scan them.

### Deviation log (after reconciliation)

The original slice is preserved above. Implementation notes:

1. **Rule chosen by the owner (2026-11-17): only `pass` clears.** This keeps
   `verdict_clears` and the gate exactly as they were (AC4: `review_evidence.py`
   is not touched by this slice) and restores conformance with ADR-0014 §3,
   whose authoring rule already said a nits-only craft/arch review is recorded
   as `pass`. No ADR change.
2. **One line beyond AC2.** spec-workflow's rule adds that a `needs-changes`
   with no `[blocker]` entry is a reviewer slip, so the pass is re-run. It
   follows from AC2 (the orchestrator never re-records a verdict) and gives the
   orchestrator a next step.
3. **Pinning test scope.** `OneBlockingRuleTests` scans `skills/*/SKILL.md`,
   `docs/workflow.md`, `templates/docs/workflow.md.template` and `agents/*.md`.
   It does not scan `skills/*/references/*.md`, `README.md`, `CLAUDE.md`, or the
   generated `hosts/` mirrors (rebuilt from `skills/`, drift-guarded by CI).
   Closed records (spec 031 slices, ADR-0014's Context section) are excluded on
   purpose (ADR-0010); `test_the_check_flags_the_old_wording` shows the check
   would flag ADR-0014's old wording, so the exclusion is what keeps it out.
4. **Changes after the compliance and craft verdicts** (both `pass`; their
   recorded bodies predate these and no further pass saw them): the
   always-true `assertIn("ADR-0014", …)` was replaced by asserting AC2's
   clauses, including that the orchestrator never re-records a verdict; the forbidden-phrase check now also catches "doesn't
   block", "do not block" and "non-blocking"; the workflow template joined the
   scan; `test_the_check_flags_the_old_wording` was added; PEP 8 blank lines
   fixed.
5. **An older test's docstring restated the old rule.**
   `SpecWorkflowSkillThreePassTests` described `needs-changes` from craft as a
   reconciliation-log entry; its docstring and comment now cite ADR-0014 §3. No
   assertion changed.
6. **Red before the change.** The three tests written first all failed
   before the change (each asserts text the slice adds, or the absence of text
   it removes). `test_the_check_flags_the_old_wording`, added after review,
   tests the checker rather than the docs, so it passes with or without the
   doc edits; it fails if the checker stops recognising the old wording.
7. **Spec close.** This slice closes spec 122. Status-board Notes carry the
   per-slice invariants. A one-line `CLAUDE.md` entry was tried and removed:
   it pushed the primer past `test_lean_primer`'s byte budget (spec 055/057),
   and the board Notes already hold the facts.
8. **Verification.** A first full run had one failure, the `CLAUDE.md` byte
   budget above. After removing that line and applying the reconciliation
   review's notes (the "never re-records" clause pinned in
   `test_spec_workflow_states_the_single_rule`, and a pointer from the block
   rule to the escalated-arch exception), the final full suite
   (`scripts/run_tests.py`) ran 5,223 tests green (8 skipped), pyright gate
   clean; host packages `--check` clean.
