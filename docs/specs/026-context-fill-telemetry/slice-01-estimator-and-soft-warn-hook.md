## Slice 026-01 — estimator-and-soft-warn-hook

**Goal:** Replace `jig-context-check.sh`'s MCP-server proxy with a
byte-based context-fill estimator and a soft warning emitted as
`additionalContext` once the loaded-bytes estimate crosses the
configured threshold. No refusal behavior — warning only.

**DoR:**
- ✅ Spec 025 (CLAUDE.md hygiene) DONE, so the primer-doc baseline
  is stable.
- ✅ Existing hook (`hooks/scripts/jig-context-check.sh`) still
  fires on `SessionStart` and is registered in `hooks/hooks.json`.

**Acceptance Criteria:**

1. **Byte-based estimate.** A new Python helper (path TBD, likely
   `scripts/context_fill.py` or `hooks/scripts/lib/context_fill.py`)
   takes the project root and returns `{bytes, est_tokens, ratio,
   threshold, breakdown}` for always-loaded artifacts: CLAUDE.md,
   `docs/memory/*.md` if present, and any file an
   `auto_attachments`-style mechanism would load. `est_tokens =
   bytes // RATIO` with `RATIO = 4` (documented as a rough
   English-prose heuristic in the module docstring).
2. **Threshold configurable via env var.** `JIG_CONTEXT_SOFT_WARN_PCT`
   overrides the default (30% of `JIG_CONTEXT_WINDOW_BYTES`, default
   sized for Opus 4.7). Both vars documented in the script header.
3. **Warning surfaced as `additionalContext`.** When `ratio >=
   threshold`, the hook emits `{"continue": true, "additionalContext":
   "..."}` naming the actual byte count, the threshold, and a
   one-sentence suggestion (run `/jig:memory-sync` and/or `/compact`).
4. **MCP-server check preserved.** Existing MCP-server-count branch
   stays (still useful for catching tool-description bloat); both
   warnings can coexist in one emission.
5. **No refusal.** The hook never sets `continue: false`. A test pins
   this.
6. **Estimator is unit-tested.** New tests assert: empty repo → 0
   bytes; CLAUDE.md only → correct byte count; mixed files → correct
   aggregation; threshold crossing emits warning; threshold not
   crossed emits nothing (or only MCP warning).
7. **No regression in existing MCP-server count tests.** Whatever
   tests currently cover `jig-context-check.sh` continue to pass.

### Deviation log (026-01)

**1. Helper path pinned to `hooks/scripts/lib/context_fill.py`.**
AC #1 listed two candidate paths (`scripts/context_fill.py` or
`hooks/scripts/lib/context_fill.py`). The implementer chose the
latter — it sits next to the consuming `jig-context-check.sh`,
making the import path (`sys.path` resolution from `BASH_SOURCE`)
self-evident, and it scopes the helper as hook-machinery rather
than a top-level script. A new `lib/` directory was created. No
`__init__.py` — Python 3.3+ namespace packages make it unnecessary
and the reviewer flagged this as a future-proofing nit only.

**2. `auto_attachments`-style files not yet measured.**
AC #1 says the estimator should cover "any file an
`auto_attachments`-style mechanism would load." Jig has no such
mechanism yet (the closest is CLAUDE.md + `docs/memory/`, already
covered). The implementer made the conservative call to measure
only CLAUDE.md + `docs/memory/*.md`. The dict shape is forward-
compatible: a future surface can extend `estimate()`'s breakdown
without changing its return contract. Compliance reviewer
confirmed this satisfies the spirit of AC #1 today.

**3. `SCRIPT_DIR` env-var pattern for plugin + scaffold install
parity.**
The slice hinted at `sys.path.insert(0, os.path.join(
CLAUDE_PROJECT_DIR, "hooks/scripts"))`. That works only in scaffold-
mode installs (where the hook lives under `.claude/`). For plugin-
mode installs (where the hook lives under `${CLAUDE_PLUGIN_ROOT}/`)
the path would miss. The implementer used `dirname
"${BASH_SOURCE[0]}"` exported as `SCRIPT_DIR`, which is robust to
both install modes. Tested end-to-end against a freshly-scaffolded
demo project.

**4. Test-runner extension (`scripts/run_tests.py`).**
The new tests live under `hooks/scripts/` and `hooks/scripts/lib/`,
neither of which the existing test runner discovered. Added a 16-
line discovery loop mirroring the existing skills loop (with the
same Python 3.11/3.12 `top_level_dir` pin). Without this, the new
tests would only run via direct `python3 …` invocation and silently
miss CI sweeps. The 1139-test count reported in the implementer
summary depends on this discovery loop being present.

**5. Scaffold-mode lib copy excludes `test_*.py`.**
`scaffold.py` was extended to copy `hooks/scripts/lib/*.py` into
scaffolded targets, but explicitly excludes `test_*.py` — scaffolded
installs ship runtime modules, not the helper's unit tests. The
glob is non-recursive (`*.py`, not `rglob`); fine today since `lib/`
is flat, but the craft reviewer flagged that a future
`lib/<subdir>/` helper would silently fail to scaffold. Not a
correctness issue today; logged here for the next refactor.

**6. Env-var naming foot-gun (`JIG_CONTEXT_SOFT_WARN_PCT`).**
AC #2 names the env var `JIG_CONTEXT_SOFT_WARN_PCT`. The "PCT"
suffix reads as "percent" but the resolver expects a fraction in
(0, 1] — typing `=30` (intending 30%) silently falls back to the
default 0.30 because the resolver treats out-of-range values as
malformed. The craft reviewer flagged this as a rename-pre-landing
candidate. Decision: **keep the spec-named env var** (faithful to
AC #2), and resolve the foot-gun via documentation. Reconciliation
applied:
  - `hooks/scripts/jig-context-check.sh` header now reads "Set as
    0.30 (not 30) — the name says 'PCT' but the value is a fraction
    in (0, 1]" + names the silent fallback behavior.
  - `hooks/scripts/lib/context_fill.py` module docstring carries
    the same clarification.

**7. RATIO de-hardcoded in the warning text.**
The craft reviewer flagged that `"4 bytes/token"` was a literal
string in the hook script while the module exported `RATIO = 4`.
If the constant ever shifts to track tokenizer empirics, the user-
facing warning would silently lie. Reconciliation: hook now
imports `RATIO` from `lib.context_fill` and interpolates it.

**8. Silent `except Exception: pass` around the estimator
branch — deliberate.**
The hook contract is "never block" (AC #5). The estimator runs
inside a try/except that swallows all failures so a broken helper
can't crash the hook surface. The craft reviewer suggested a
debug-mode stderr branch (e.g., `JIG_CONTEXT_DEBUG=1`); declined
for scope — adds an env var the slice doesn't require. Logged here
so a future maintainer doesn't try to "fix" the silent swallow.

**9. Reviewer-flagged future-polish items (not addressed,
intentionally).**
The craft reviewer noted four items worth flagging but explicitly
out of scope for 026-01:
  - **Per-file breakdown surfacing** in the warning text. Today
    the warning shows only the byte total. Surfacing top-N
    contributors would speed up `/jig:memory-sync` triage. Future
    polish slice.
  - **End-to-end scaffold test** that actually executes the
    scaffolded hook. Current test verifies file presence + byte
    identity, not runtime behavior. The source-tree integration
    test (`test_jig_context_check.py`) covers the runtime path.
  - **`rglob` switch + `__pycache__` filter** in scaffold's lib
    copy, for future `lib/<subdir>/` helpers.
  - **`__init__.py` in `hooks/scripts/lib/`.** Implicit namespace
    packages work today; adding one would be defensive against
    zipapp packaging / frozen importers.

**10. `verify_install.py` does not check the new `lib/`
machinery.**
Compliance reviewer flagged that `scripts/verify_install.py`
(the user-facing post-install diagnostic) does not verify
`.claude/hooks/scripts/lib/context_fill.py` was copied. The
scaffold test pins this internally, but a future regression in the
copy logic would not show in `verify_install` output. Logged as a
follow-up; not required for this slice's ACs.
