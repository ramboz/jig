### Deviation log (after reconciliation)

The original spec is preserved above. Implementation notes:

**1. Four options enumerated, not two.** Spec 036's decomposition
and this slice's AC #2 framed the choice as Option A (immutable)
vs Option B (`## Amendments`). The ADR landed enumerates **four**:
A (immutable), B (amendments), C (hybrid — amendments default +
new-ADR carve-out for decision content), and D (status quo). The
Recommended Decision picks **C**. Rationale: A and B are the
canonical poles; C is a small, principled middle that handles
100% of the actual workload (all five live drifts are prose) at
B's cost; D is included for completeness so consequences of
inaction are explicit. AC #2 is met in spirit (both poles are
present with cost / discoverability / audit-trail consequences);
AC #5's binary framing ("If Option B chosen, ADR specifies the
amendment-entry shape… If Option A chosen, this AC reduces to a
one-line note") is met because C inherits B's amendment mechanism
and the ADR provides the dated-entry shape in Option B's
worked-example block.

**2. Scope tightened: DONE/SUPERSEDED, not RECONCILED.** Both the
arch-review and pr-review passes independently flagged that
slice AC #4(a) says "RECONCILED specs in scope" but the ADR
scopes to `DONE` / `SUPERSEDED` and lists `RECONCILED` as
out-of-scope. The ADR is correct: `RECONCILED` is a transient
lifecycle step (`RECONCILED → DONE` per `skills/spec-workflow/
SKILL.md`), not a terminal state. The AC wording inherited stale
phrasing from spec 036's clarification Q1, which used
"RECONCILED" colloquially to mean "closed / finalized." This is
an authoring tightening, not a substantive deviation from intent.
**Downstream impact:** slice 036-02's sweep targets DONE specs,
not RECONCILED ones. Same set in practice (no spec sits at
RECONCILED for long), but the language matters for the
reconciliation-checklist line.

**3. Reviewer findings addressed via cosmetic post-accept edits.**
The compliance pass surfaced two specific issues that were fixed
before the arch/craft passes ran:
   - **Placeholder path in Option B's worked example** (originally
     `../../specs/005-.../slice-03-...md`) replaced with the real
     relative path `../005-adr-workflow/spec.md` and clarified by
     a trailing parenthetical noting that real-amendment paths
     are relative to the amended artifact. (The pr-review pass
     later suggested using the per-slice file convention; declined
     because spec 005 is in the legacy embedded-format layout —
     no sibling slice files exist — and the link as written is
     correct for that layout.)
   - **ADR-0006 carve-out characterization** tightened to name
     Option A (lifecycle) and Option C (Context cosmetic edits)
     explicitly, instead of summarizing both as "preview-then-
     accept with an exception."
   Both edits are to prose in Decision Options Considered and
   Recommended Decision, not to the substance of ADR-0008's own
   decision. Per ADR-0006's narrow-carve-out spirit, edits that
   don't change decision substance are permissible post-accept;
   this case is at the same boundary that motivated ADR-0006.
   The meta-irony (editing post-accept text in the same ADR that
   regulates post-accept editing) is acknowledged and noted here
   for the record.

**4. Strengths flagged for future ADR authoring.** Both
reviewers called out patterns worth repeating: rigorous option
enumeration with consistent cost/discoverability/audit-trail
axes; an explicit relationship-graph section naming downstream
consumers; deferring tooling until the rule is observed to fail
(Hippocratic restraint); using a concrete, recent, self-
implicating dogfooding example; and providing a "working rule"
test for fuzzy boundaries. These are not deviations — they're
the gold-standard shape the next policy ADR should match.
