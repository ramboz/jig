## Slice 029-01 — kind-frontmatter-and-body-shape

**Goal:** Promote SPIDR's "S" axis from teaching to runtime by adding
a typed `kind` enum field to slice frontmatter (with `spike` as its
first non-default value), documenting the four-block body shape
(Question / Time-box / Findings / Outcome) in the slice template and
spec-workflow SKILL.md, and teaching `spec_lint.py` to validate both
the enum and the body shape for `kind: spike` slices. After this
slice lands, a spike-shaped slice can be authored, validated, and
reviewed end-to-end without the contortions that today's
feature-shaped slice forces on research work.

**DoR:**
- ✅ Per-slice frontmatter pattern from [spec 015](../015-structured-lifecycle-metadata/spec.md)
  is in place and `spec_lint.py` already validates the existing
  fields.
- ✅ SPIDR primer at [docs/spec-workflow/spidr-primer.md](../../spec-workflow/spidr-primer.md)
  documents the five techniques.
- ✅ Dual-read slice parsing from [spec 018](../018-slice-per-file/spec.md)

  Overview: typed (not body-only), always-nested (no
  `docs/spikes/`), manual reshape (no auto-cascade).

**Acceptance Criteria:**

1. **`kind` enum accepted in slice frontmatter, default unset.** A
   slice with `kind: spike` parses cleanly via `_common/parsing.py`;
   a slice without `kind:` parses identically to today (no
   regression). `kind: feature` is also accepted as a documented
   explicit-default synonym for unset, but the template does not
   include the field by default.
2. **`spec_lint.py` validates the enum.** A slice with an unknown
   `kind:` value (e.g., `kind: bogus`) is rejected with a clear
   error naming the allowed values (`spike`, `feature`). The CI
   path that runs `spec_lint` in [spec 013](../013-release-pipeline/spec.md)'s
   pipeline catches this on PR + push:main.
3. **Body-shape soft-warn for `kind: spike`.** When `spec_lint`
   sees `kind: spike` and the body is missing any of the four
   labelled blocks (`**Question:**`, `**Time-box:**`, `**Findings:**`,
   `**Outcome:**`), it emits a **warning** (not a hard failure)
   naming the missing label(s). Spikes mid-flight legitimately have
   empty Findings/Outcome — warnings, not errors.
4. **Slice template documents the spike body shape.** `templates/docs/specs/slice-template.md`
   gains a "For `kind: spike` slices" subsection showing the four
   labelled blocks with brief explanations (when each is filled,
   what shape Outcome takes).
5. **SPIDR primer extension.** `docs/spec-workflow/spidr-primer.md`
   gains an explicit "when the S axis fires during decomposition,
   the resulting slice is `kind: spike`" rule with a worked example
   (one-paragraph spike from a plausible spec).
6. **spec-workflow SKILL.md guidance.** `skills/spec-workflow/SKILL.md`
   gains a "Spike slices" subsection covering: (a) when to
   introduce one during decomposition, (b) the body shape with the
   four labels, (c) the always-nested rule (no standalone
   `docs/spikes/`), (d) the abandoned-spike manual reshape pattern.
7. **Outcome field shape documented.** Body-shape docs (template +
   SKILL.md + SPIDR primer) all agree on the three Outcome forms:
   `ADR-NNNN created`, `spec NNN-NN unblocked`, `abandoned (reason)`.
   Multiple outcomes separated by `;` are explicitly supported (e.g.,
   `ADR-0007 created; spec 030-02 unblocked`).
8. **Worked example in the SPIDR primer.** A short illustrative
   spike — one-sentence Question, plausible Time-box, two-bullet
   Findings, single Outcome — appears as an aside in the SPIDR
   primer so new contributors see the shape end-to-end.
