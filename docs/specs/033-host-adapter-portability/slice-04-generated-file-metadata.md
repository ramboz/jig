## Slice 033-04 - generated-file-metadata

**Goal:** Add compact managed-file metadata for scaffolded runtime files
so future update tooling can distinguish jig-managed output from
user-owned edits.

**DoR:**
- Slice 033-03 is DONE.
- The scaffold renderer boundary identifies every generated file family.

**Acceptance Criteria:**

1. **Managed file policy documented.** Architecture docs define which
   generated files get inline markers, which are tracked only in a
   manifest, and why.
2. **Compact metadata implemented.** Scaffolded managed files or
   `scaffold.json` record enough information to identify the source
   jig version, host renderer, source template/path, and content hash.
3. **Token budget respected.** Large prose files do not gain noisy
   banners when the same metadata can live in a manifest without
   reducing update safety.
4. **Existing Claude output remains readable.** The metadata does not
   make `CLAUDE.md`, `AGENTS.md`, skills, or agent prompts meaningfully
   harder for an LLM to use.
5. **Rerun behavior tested.** Re-running scaffold over untouched managed
   files is idempotent; re-running over user-edited managed files either
   preserves the edit or refuses with a clear message according to the
   documented policy.
6. **Future update path captured.** Any remaining work for `jig update`
   is parked in `docs/refinement-todo.md` with a resolution trigger.

**DoD:**
- [ ] All ACs pass; full test suite green (no regressions).
- [ ] Implementer test coverage exercises each AC with at least one
      fixture.
- [ ] Reviewed by `reviewer` subagent. Reviewer prompt built by
      `review.py`.
- [ ] Implementation review passed.
- [ ] Deviation log produced under this slice heading.
- [ ] Reconciliation review passed.

      during implementation.

### Close-out (post-DONE)

the same Claude scaffold, but the generated files now carry the evidence
needed for safe future updates and future host adapters.
