## Slice 109-01 — arch-pass-leanness-lens

**Goal:** The arch-review pass explicitly evaluates whether a *simpler*
architecture would satisfy the acceptance criteria — surfacing over-engineering,
premature abstraction, and speculative generality — so leanness becomes a
standing review lens instead of a value re-derived ad hoc.

**DoR:**
- ✅ Insertion points confirmed: `build_arch_review_prompt`
  ([review.py:996](../../../skills/independent-review/review.py), `## Evaluate`
  block ~L1088) and `skills/arch-review/SKILL.md` baseline buckets (no leanness
  language today — verified by grep).

**Acceptance Criteria:**

1. **The arch prompt evaluates for leanness.** `build_arch_review_prompt`'s
   emitted prompt gains an evaluation directive asking whether a simpler
   architecture satisfies the same acceptance criteria, and to flag
   over-engineering / premature abstraction / speculative generality
   (unnecessary indirection, config knobs, or extension points with no current
   caller). It sits in the `## Evaluate` block, alongside the existing
   boundary/contract questions.
2. **The arch-review baseline bucket carries it too.** `skills/arch-review/SKILL.md`'s
   baseline rubric directs the reviewer to raise minimal-viable-architecture /
   over-engineering issues under its **Concerns** bucket (so a reviewer applying
   the bundled baseline — not just the `review.py` prompt — checks leanness).
3. **No new gate, flag, or output shape.** The lens reuses the existing arch
   verdict envelope: over-engineering findings are ordinary `[blocker]`/`[nit]`
   SPECIFIC-ISSUES entries. `build_arch_review_prompt`'s signature is unchanged,
   no new frontmatter key is introduced, and the arch pass stays gated on the
   existing `arch_review: true` flag (no always-on escalation).
4. **The leanness directive is anchored, not free-floating.** The wording ties
   "simpler" to *satisfying the ACs* (leaner-that-still-passes, not
   leaner-at-any-cost), so the lens cannot be read as license to strip required
   behavior.
