## Slice 058-06 — `jig:bug-fix` skill + plugin wiring + workflow.md routing

**Goal:** ship the user-facing `jig:bug-fix` skill that orchestrates the
`bug.py` lifecycle, wire it into the plugin + scaffold/migrate machinery,
and add the routing paragraph that closes the loop — bug-shaped work goes
here, not through specs.

**DoR:**
- ✅ 058-02..05 (the `bug.py` helper is complete enough to document and
  orchestrate).

**Acceptance Criteria:**

1. **`skills/bug-fix/SKILL.md` exists** with `name: jig:bug-fix`, a
   trigger-rich description (auto-fires on "fix this bug", "debug this",
   "root-cause this", "this regressed"), and the orchestration: the
   lifecycle + teeth gates, the `diagnose` vs `diagnose_and_fix` modes,
   the borrowed diagnostic question ("output vs the process that created
   it"), the tier model, and the de-escalation guidance. It **owns its
   orchestration** (does not defer wholesale); only the reused craft
   (`pr-review`) and conditional security (`security-review`) steps defer
   to a richer installed skill.
2. **Plugin wiring:** the skill is registered in the plugin manifest /
   marketplace listing, and `migrate copy-machinery` + scaffold-init copy
   `skills/bug-fix/` and `bug.py` into a target's `.claude/` under the
   appropriate tier (per ADR-0012); `scripts/verify_install.py` asserts
   its presence.
3. **`docs/workflow.md` gains a routing rule:** a short section stating
   that bug-shaped work goes through `jig:bug-fix` (proportional to
   tier — trivial bugs skip straight to `tdd-loop` + commit), and
   spec-shaped work (hard-to-reverse decisions, cross-layer, ambiguous
   scope) goes through `spec-workflow`. This is the bookend to the
   spec-workflow "do not use for bug-shaped work" clause.
4. **Cross-references updated:** the project `CLAUDE.md` Skills table, the
   `templates/CLAUDE.md.template` (if the skill ships in the scaffolded
   tier), and the `spec-workflow` / README pointers reference the new
   skill by its real name.
