## Slice 032-02 — scaffold-completion-marker

**Goal:** Make `scaffold.json` the completion sentinel for `scaffold()` —
write it LAST, after all docs, CLAUDE.md, brief.md, and machinery copies.
After this slice, if `scaffold()` is interrupted (Ctrl-C, crash) before
the final `scaffold.json` write, the partial state has no
`scaffold.json`, so a re-run is re-runnable without `--force` (the
existing "already scaffolded" check, which gates on `scaffold.json`
presence, naturally allows the resumption).

**DoR:**
- ⏳ Slice 032-01 DONE (the `atomic_write_text` helper exists;
  `scaffold.json` write uses it; an interrupted `os.replace` of
  `scaffold.json` either fully writes or fully doesn't).
- ✅ The "already scaffolded" check today keys on `scaffold.json`
  presence (confirmed in `scaffold.py:_looks_already_scaffolded`).

**Anti-horizontal-phasing check.** Vertical: a user runs `scaffold-init
<target>`, and the process is interrupted halfway through (e.g., Ctrl-C
during the `--with-machinery` copy of skill dirs). On the next run,
scaffold-init finds no `scaffold.json`, treats the partial directory as
un-scaffolded, and proceeds (idempotently re-creating any docs/* and
re-copying any machinery without `--force`). Crosses all layers:
`scaffold.py` write ordering (modified), the on-disk filesystem state
across two runs (existing — but now exploits the sentinel), and the
user's recovery experience (no manual cleanup needed).

**Acceptance Criteria:**

1. **`scaffold()` writes `scaffold.json` last.** The function is reordered
   so the `scaffold.json` write is the FINAL filesystem mutation in the
   happy path. All other writes (CLAUDE.md, docs/*, brief.md,
   `.claude/skills/*`, `.claude/agents/*`, `.claude/hooks/scripts/*`,
   `.claude/settings.json`) complete before `scaffold.json` is written.

2. **A crash before `scaffold.json` is written leaves a re-runnable
   state.** A test simulates an interrupted scaffold by monkey-patching
   the `atomic_write_text` call for `scaffold.json` to raise, then
   re-runs `scaffold()` on the same target without `--force`. The re-run
   succeeds (does not raise `AlreadyScaffoldedError`) and produces a
   well-formed final scaffold.

3. **Idempotency: a successful scaffold followed by a re-run still
   raises `AlreadyScaffoldedError` without `--force`.** Regression
   guard — the marker still gates re-runs once written.

4. **No new flag, no new env var, no new sentinel infrastructure.** The
   existing `scaffold.json` presence check IS the marker. The scope of
   this slice is write-ordering only.

5. **Partial-state-on-refuse path stays consistent.** AC #4 of slice
   016-02 introduced `UnmanagedHooksError` which today is raised AFTER
   `.claude/hooks/scripts/` is already copied (deviation log §7 of
   016-03 records this rough edge). With `scaffold.json` written last, a
   refused scaffold leaves the machinery copy but no `scaffold.json` —
   the next run treats it as un-scaffolded and re-attempts, which is the
   correct recovery. A test pins this behavior:
   `UnmanagedHooksError` → no `scaffold.json` → re-run succeeds.

6. **No regression in existing tests.** Full suite green. The
   `--force` re-scaffold tests (slice 016-02 / 016-03) still pass with
   the new write order.

### Deviation log (after reconciliation)

The original spec is preserved above. Implementation notes:

**§1 — Pre-edit write order.** Before this slice, `scaffold()` wrote
files in this order:

1. `CLAUDE.md` (line 813 of pre-edit `scaffold.py`)
2. `docs/*.md` (recursive template loop)
3. `.claude/hooks/` directory creation
4. `scaffold.json` (line 853)
5. `brief.md` (line 861)
6. `copy_machinery(...)` — which writes hook scripts + settings.json
   (line 872, conditional on `--with-machinery`)

So `scaffold.json` was the **fourth** write, with `brief.md` and the
entire machinery copy happening AFTER it. This made it impossible to use
`scaffold.json` as a completion sentinel: a crash during machinery copy
would leave a `scaffold.json` on disk, so a re-run would (correctly)
raise `AlreadyScaffoldedError` and require `--force` — exactly the rough
edge slice 016-03 deviation §7 named.

**§2 — Post-edit write order.** The reorder moves `scaffold.json` to
the LAST mutation. New order:

1. `CLAUDE.md`
2. `docs/*.md`
3. `.claude/hooks/` directory creation
4. `brief.md`
5. `copy_machinery(...)` (conditional on `--with-machinery`)
6. `scaffold.json` — **completion sentinel, last write**

The reorder is a pure code-block move within `scaffold()`; no helper
signatures change, no new state machinery, no new conditionals around
`--with-machinery` (the existing `if with_machinery:` block stays where
it is, just before the scaffold.json block now instead of after).

**§3 — Anticipated-but-not-spec'd issue: `_looks_already_spec_driven`
also gates re-runs.** The slice goal frames the recovery path around
"the existing 'already scaffolded' check, which gates on `scaffold.json`
presence, naturally allows the resumption" — but there are TWO gates in
`scaffold()`, not one:

  (a) `AlreadyScaffoldedError` on `scaffold.json` presence (the gate the
      slice describes).
  (b) `LooksAlreadySpecDrivenError` from slice 008-05, which fires when
      ≥3 of `docs/specs/`, `docs/decisions/`, `docs/workflow.md`,
      `docs/architecture.md` are present **even without** a
      `scaffold.json`.

After a partial-scaffold crash, all four 008-05 triggers are on disk
(scaffold writes them BEFORE `scaffold.json`, by design). So a naive
write-reorder would route the user to `/jig:migrate` instead of
re-running scaffold — the opposite of AC #2's promise.

**§4 — Resolution: jig-watermark gate.** Added a small helper
`_is_jig_partial_state(target)` that returns True iff `target/CLAUDE.md`
exists AND contains the literal watermark `Generated by [jig]` (a
string already present in `templates/CLAUDE.md.template`). The
`_looks_already_spec_driven` check is now skipped when
`_is_jig_partial_state(target)` is True — that's a crashed mid-scaffold,
not a user's pre-existing spec-driven project.

This is arguably scope-adjacent (AC #4 says "no new sentinel
infrastructure") but reads as a clarification of the existing gating
logic rather than new infrastructure: we're reading an existing
artifact (`CLAUDE.md`) for an existing string. Without it, AC #2's
load-bearing claim ("re-run without `--force` succeeds") fails because
`LooksAlreadySpecDrivenError` fires first. The alternative — leaving
the deviation un-fixed and forcing users to `--force` — would defeat
the slice's stated goal.

The gate is conservative: a CLAUDE.md without the jig watermark (e.g.,
a user's hand-written one) falls through to `_looks_already_spec_driven`
as before, so users with their own CLAUDE.md and a spec-driven layout
still get routed to `/jig:migrate`. The watermark string is documented
in a module-level constant `_JIG_CLAUDE_MD_WATERMARK` for future
discoverability.

**§5 — Test count delta.** +2 tests (1300 → 1302). Both added to
`skills/scaffold-init/test_scaffold_mode.py` in a new test class
`ScaffoldCompletionMarkerTests`:
  - `test_crash_before_scaffold_json_leaves_rerunnable_state` (AC #2)
  - `test_unmanaged_hooks_error_leaves_rerunnable_state` (AC #5)

The AC #2 test imports `scaffold` directly to monkey-patch
`atomic_write_text`; the AC #5 test stays subprocess-based (no patching
needed — `UnmanagedHooksError` is reachable from the CLI). Both leave
no global state behind: AC #2 restores `atomic_write_text` in a
`try/finally`.

**§6 — Idempotency regression (AC #3).** The existing
`test_refuses_to_overwrite_existing_scaffold` in `test_scaffold.py`
already pins this. No new test needed; it passed unchanged after the
reorder — `AlreadyScaffoldedError` still fires when a completed
scaffold is re-run without `--force`.

**§7 — Sites where reordering was nontrivial.** None. The
`if with_machinery:` block was already conditional and self-contained;
moving the `scaffold.json` write past it required no signature changes,
no new flags, no conditional duplication. The `_render_brief` call
already operates on the in-memory `signals/installed_tiers/offered_tiers`
tuple, so reordering brief.md before the scaffold.json write didn't
require recomputing any state.

**§8 — Open question (not blocking).** `_is_jig_partial_state` reads
CLAUDE.md every scaffold run. The read is cheap (a few KB), but if the
file is huge or unreadable, the `OSError` path returns False, which
falls through to `_looks_already_spec_driven`. That's the safe default
(false-positive-routes-to-migrate, per the existing `_looks_already_spec_driven`
docstring philosophy). No follow-up needed.
