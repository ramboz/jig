## Slice 048-06 — scaffold-completion-verification

**Goal:** Give the user a deterministic "your scaffold is complete and
wired" signal at the end of `/jig:scaffold-init`, by **running the
verification that already exists** (`verify_install.py`'s scaffold-mode
checks) and surfacing a pass/fail summary. This is the assurance that was
missing when a scaffolded project "felt unwired" — the checks existed as
a dev/CI tool but never ran for the user at scaffold time.

**DoR:**
- ✅ `scripts/verify_install.py` already ships scaffold-mode checks
  (slice 016-03): `run_all_scaffold_checks` over skills / agents / hook
  scripts / settings registration.
- ✅ Slice 048-05 defines the seed artifacts the verifier should expect.
- ✅ Coordinated with spec 047 (install contract verification) — the
  contract definition stays owned by 047; this slice **calls** the
  verifier, it does not define a parallel one.

**Acceptance Criteria:**

1. **Verification runs at scaffold end.** After `scaffold.py` finishes
   writing artifacts, it invokes the existing scaffold-mode checks and
   prints a compact, human-readable summary (per-check pass/fail + an
   overall verdict) to stdout as part of the wizard's closing report.
2. **Reuse, don't duplicate.** The check logic is the existing
   `verify_install.py` scaffold path (or 047's contract validator once it
   lands). This slice adds the *invocation + reporting*, not a second
   definition of "what a complete scaffold is." If 047 has landed, prefer
   its validator; otherwise call `run_all_scaffold_checks`.
3. **The seed is in the expected set.** The verifier's scaffold
   expectations include the slice 048-05 seed (`001-adopt-jig/spec.md`,
   `slice-01-bootstrap.md`, populated status board, `002-first-spec`
   stub), so a scaffold missing the worked example fails verification.
4. **A failed check is loud and actionable.** If any check fails, the
   wizard's exit status and summary make the failure unmistakable and
   name what is missing — never a silent partial scaffold.
5. **No new skill.** This is a behavior of the existing `scaffold-init`
   helper + `verify_install.py`. No new `/jig:` skill, no new skill
   directory.
6. **Tests cover the wired-in run.** A test scaffolds a temporary project
   and asserts the completion summary is emitted, reports success on a
   good scaffold, and fails loudly when a required artifact (including a
   seed file) is removed.

**Non-goals:**

- **No re-runnable on-demand verification skill.** A user-facing "check
  whether my project is still correctly wired" command is **deferred**
  until the signal hits (a user actually reports drift / asks the
  question). Record it in `docs/refinement-todo.md` with that resolution
  trigger during implementation; do not build it now.
- **No contract redefinition.** Spec 047 owns the contract surface.

### Deviation log (after reconciliation)

The original spec is preserved above. Implementation notes:

1. **Reuse, not redefine (AC #2).** `run_completion_summary` in
   `scripts/verify_install.py` composes the existing `_SCAFFOLD_CHECKS`
   table plus one new `check_scaffold_seed_present`; it does not redefine
   "a complete scaffold." `scaffold.py`'s `main()` lazily imports
   `verify_install` (via a `sys.path.insert` to `scripts/`) and calls it
   as the closing report — same cross-dir local-import pattern `migrate.py`
   already uses to reach `scaffold.py`.

2. **Mode-awareness (load-bearing correctness).** The four machinery
   checks (`skills`/`agents`/`hooks`/`settings`) validate `.claude/`
   artifacts that exist only in `--with-machinery` mode, so they run only
   when `with_machinery=True`. In `--plugin-only` mode the machinery lives
   in the installed plugin; running those checks would false-fail a good
   plugin-only scaffold, so they are skipped. The seed/docs check runs in
   both modes. Verified by `test_plugin_only_good_scaffold_passes_without_machinery_false_fail`.

3. **Greenfield ordering.** `seed_expected = not _specs_dir_has_content(target)`
   is sampled in `main()` BEFORE `scaffold()` writes the seed — the only
   ordering that distinguishes "seed dropped" (failure) from "seed
   legitimately skipped on a non-greenfield target" (not a failure). After
   scaffold writes, the predicate would always be True. Pinned by
   `test_non_greenfield_skipped_seed_is_not_a_failure`.

4. **New exit code 4 (reviewer reconciliation note).** Verification
   failure returns exit **4** from `main()`, distinct from 1 (scaffold
   raised) and 3 (refusal) / 2 (argparse). No existing contract declared
   scaffold.py's exit codes, so nothing is contradicted, but the code was
   previously undocumented. Recorded here as the effective contract:
   **0** ok · **1** scaffold exception · **2** argparse usage · **3**
   refusal (already-scaffolded / looks-spec-driven) · **4** artifacts
   written but completion verification failed. Discoverable here rather
   than churning the module docstring.

5. **Degenerate-but-valid case considered.** `--plugin-only` + non-greenfield
   (machinery checks skipped AND seed skipped) yields a "0/0 checks passed"
   summary and returns 0. This is intentional and explicitly non-silent
   (the summary prints why no checks applied), not a swallowed failure.

6. **Deferral recorded (Non-goal).** The re-runnable on-demand verification
   command is deferred to `docs/refinement-todo.md` § Architecture with the
   resolution trigger "a user reports drift / asks 'is my project still
   wired?'". The plumbing (`run_completion_summary` + `verify_install.py
   --mode scaffold`) already exists, so a future `/jig:` surface would be
   mostly exposure, not new logic. Nothing parked to `docs/inbox.md`.
