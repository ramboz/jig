**Acceptance Criteria:**

1. **`skills/contracts/SKILL.md` is no longer a stub.** Frontmatter `disable-model-invocation: true` is removed; the skill auto-triggers on contract-shaped requests. `description:` is rewritten to advertise the new framing (recommendation per surface, nudge-don't-force, orchestrates ecosystem tools).
2. **Per-surface recommendation table.** Markdown table with at least these surface types: HTTP API, event bus, RPC, GraphQL, internal data shapes, config / env vars. Each row has columns: surface type, recommended artifact, validation tool, codegen tool (or "none / per-stack"), one-line rationale. Coverage extends to at least 6 rows.
3. **"Nudge, don't mandate" language is explicit.** The SKILL.md body contains an explicit "when to opt out" subsection covering migration scenarios with pre-existing bespoke contract patterns. The reviewer-prompt and wizard touchpoints (022-02) are noted as the structural enforcement, not jig refusing edits.
4. **Worked example #1 — OpenAPI for HTTP API.** A sibling `skills/contracts/worked-example-openapi-http.md` file walks through extracting an OpenAPI spec from a prose API contract (using aso-shallow-validator's §5 as the source-of-record). Shows before (prose jsonc) → after (openapi.yaml fragment), the `spectral` CI gate wiring, and the `openapi-typescript` codegen call.
5. **Worked example #2 — JSON Schema for internal data envelope.** A sibling `skills/contracts/worked-example-json-schema-envelope.md` walks through pinning an internal data shape with JSON Schema. Shows the schema file, `ajv` validation in test, and a note on stack-coupled alternatives (Zod / Pydantic / TypeBox) where the ecosystem makes a different choice idiomatic.
6. **Deferral language for richer alternatives.** SKILL.md `description:` includes a deferral hint analogous to 012-01 / 014-01: "Defers to any other installed skill whose description identifies it as handling contract artifacts, schema validation, or API contract review." Allows users to install a richer `~/.claude/skills/contracts/` skill that takes precedence.
7. **Surface-pinning tests.** A new test class (e.g. `ContractsSkillTests`) pins:
   (a) frontmatter no longer has `disable-model-invocation: true`;
   (b) the per-surface table heading + at least 6 surface-type tokens;
   (c) both worked-example files exist with key tokens;
   (d) the "nudge, don't mandate" / "when to opt out" language is present;
   (e) the deferral hint phrase is in the description;
   (f) the description mentions key triggers (OpenAPI, JSON Schema, contract artifacts, schema validation).
   Bonus: anti-greediness class (mirror `DescriptionBoundsTests` from 012-01) pins against over-claiming phrases like "scaffolds your contracts" or "generates OpenAPI for you" (the skill recommends, doesn't generate).
8. **No `.py` changes.** All deliverables are markdown. `skills/contracts/` does not gain a `contracts.py` helper.

### Deviation log (after reconciliation)

The original spec is preserved above. Implementation notes follow:

**§1 — Worked-example file naming.** The two worked examples ship as siblings under `skills/contracts/`: `worked-example-openapi-http.md` (AC #4) and `worked-example-json-schema-envelope.md` (AC #5). Matches the precedent set by `skills/vision-elicitation/worked-example-*.md` files from spec 017-02 (rather than an inline `## Worked example` body section).

**§2 — Test file named `test_contracts_skill_surface.py`, not `test_skill_surface.py`.** Initial draft used the shorter `test_skill_surface.py` name (matching pr-review's local convention) but the project's `python3 -m unittest discover -s skills/` invocation collides on module-basename uniqueness across discovery roots, so the suite refused to start. Renamed to `test_contracts_skill_surface.py`, matching arch-review (`test_arch_review_skill_surface.py`) and vision-elicitation (`test_vision_elicitation_skill_surface.py`) — both of which face the same multi-skill-discovery constraint. pr-review gets to use the short name only because it's the alphabetically-first skill with a `test_skill_surface.py`. Recorded so future SKILL.md-only skills don't repeat the rename round-trip.

**§3 — AC #5 interpretation: "different ecosystem shapes" → "different surface shapes."** AC #5 reads "Worked example #2 — JSON Schema for internal data envelope … a sibling … walks through pinning an internal data shape with JSON Schema. Shows the schema file, `ajv` validation in test, and a note on stack-coupled alternatives (Zod / Pydantic / TypeBox) where the ecosystem makes a different choice idiomatic." The spirit of AC #5 (and the spec's `## Goals` #3 phrasing "in different ecosystem shapes") was to demonstrate the abstraction holds across stacks. The implementation delivers **surface-shape** differentiation (HTTP API vs. internal data envelope) using JS/Node tooling in both code blocks; stack-coupled alternatives (Zod / Pydantic / TypeBox) appear in prose in example #2, not as a second worked example in Python or Go. The reviewer correctly flagged the framing tension: "different ecosystem shapes" overpromises relative to what the implementation demonstrates. Reconciliation rewrote the `## Worked examples` body section in SKILL.md to honestly describe what's shown — "intentionally on different **external surfaces**" — and added a stack-agnosticity note pointing at where the same recommendations apply in Go/Python/Rust. AC #5 is met (file exists, JSON Schema artifact + ajv + stack-coupled-alternatives all present); the framing tension is resolved by tightening the prose rather than rewriting the worked example in a second language.

**§4 — Description length (~1157 chars) is on the long end of the precedent envelope.** pr-review ships ~785 chars, arch-review ~915 chars; contracts ships ~1157 chars. Drivers of the additional length: (a) per-surface artifact recommendations require naming five artifact types up-front (OpenAPI / JSON Schema / AsyncAPI / .proto / GraphQL SDL), where pr-review/arch-review each name a single output shape; (b) the ecosystem-tool orchestration claim requires naming the canonical tools (spectral / ajv / buf / graphql-inspector); (c) three "do not use for" carve-outs cover the wider concept-collision space (internal-module-boundary refactoring, scaffolding a contracts/ dir, auto-generating schemas). Accepted as-is; will trim if the router shows over-triggering against richer user-installed skills (the AC #6 deferral hint should handle category-based deferral first).

**§5 — `DescriptionBoundsTests` carries two pr-review-precedent phrases ("expert-level", "multi-persona") that aren't contracts-specific.** Both are stylistic carryovers from pr-review's 012-01 anti-greediness pattern. "multi-persona" remains defensible for contracts (the ADR-0002 kitchen-sink concept could re-emerge as "review contracts from security + reliability + observability personas," which is the over-claim shape we'd want blocked); "expert-level" is purely stylistic. Kept both — they're cheap to retain and don't false-fail today. Recorded as a "copied from precedent verbatim" data point for future skills that may want anti-greediness language unique to their domain.

**§6 — Reviewer-flagged: env-contract row link pointed at ADR-0005, not at the pattern's canonical source.** Per the implementation reviewer's SPECIFIC ISSUE #1, the Config / env-vars row's "[aso-shallow-validator env-contract pattern](…)" linked at ADR-0005 — but ADR-0005 only *mentions* the pattern; it isn't the pattern's documentation. Fixed in reconciliation: rewrote the row's rationale to describe the env-contract triple inline ("markdown reference table + `.env.example` seed + stdlib-only checker script + CI gate") and demoted the ADR-0005 link to a "see Context §1 for the case study that motivated this row" pointer. Avoids cross-project relative-path fragility (a `../../../aso-shallow-validator/...` link would only resolve in the author's dev setup) and an external GitHub URL would pin to a specific upstream repo path.

**§7 — Reviewer-flagged: `test_table_has_required_columns` was a weak surface assertion.** Per the implementation reviewer's SPECIFIC ISSUE #4, the original test checked that "surface", "artifact", "validation", "codegen", "rationale" tokens appeared anywhere in `body_lower`. Reviewer correctly noted those tokens also appear in body prose around the table, so deleting the table would still pass the test. Reconciliation added `test_table_header_row_locked` — a regex (`\|[^|\n]*surface[^|\n]*\|[^|\n]*artifact[^|\n]*\|…`) that requires the five concept tokens to appear together in a single pipe-delimited markdown header row. Kept the weaker test alongside as a wider safety net. Test count 42 → 43.

**§8 — Reviewer-flagged: `worked-example-openapi-http.md:7` uses a `https://github.com/...` URL for the aso-shallow-validator source-of-record link.** Per the implementation reviewer's SPECIFIC ISSUE #5, the rest of the spec/SKILL.md uses relative paths for inter-doc references. Kept the github URL deliberately: the worked example is shipped to downstream projects via the jig plugin, and a relative path like `../../../aso-shallow-validator/...` only resolves in the author's local dev tree (where jig and aso-shallow-validator happen to be siblings). For downstream installers, the github URL is the only address that resolves at all. Recorded the rationale so future worked examples that cite external real-world sources can follow the same convention.

Not a slice-landing blocker; lands after the slice transitions to DONE.
