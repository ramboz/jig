## Slice 052-03 — destructive-command-guardrail

**Goal:** A freshly scaffolded project's `settings.json` denies the
dangerous git/file commands by default, so an accidental force-push /
hard-reset / `rm -rf` is refused without relying on the agent reading a
rule.

**DoR:**
- ✅ Slice 052-01's ADR is Accepted (floor scope incl. the permissions
  posture decided).
- ✅ `scaffold.py`'s marker-based `settings.json` merge (slice 016-02) is
  the integration point.

**Acceptance Criteria:**

1. **Conservative deny defaults are scaffolded.** `scaffold-init` writes a
   `permissions.deny` array into `.claude/settings.json` covering at least
   force-push, hard-reset, and `rm -rf` (the guidelines `permissions.md`
   conservative project default), using deny-glob shapes that match the
   documented dangerous forms.
2. **Merge is non-destructive + marker-tracked.** The deny rules merge into
   an existing `settings.json` without dropping user-added `permissions`
   entries, using the same jig-managed marker mechanism as the hooks block;
   re-running scaffold is idempotent.
3. **Honest framing.** The accompanying comment/doc states deny-globs are
   defense-in-depth — they can miss flag permutations (e.g.
   `git push origin main --force`) — so the primary control remains
   behavioral + out-of-band, per `permissions.md` ("deny rules are
   defense-in-depth, not a firewall") and 052-01.
4. **Tests cover it.** Scaffold tests assert the deny array is present in a
   fresh scaffold and is preserved/merged (not duplicated, not clobbering
   user entries) when `settings.json` pre-exists.
