## Slice 030-01 — rollup-on-transition-and-regen

**Goal:** Wire spec.md frontmatter `status:` to auto-derive from slice
states, written at two trigger points (`transition` after a slice
mutation; `status-board` during regen) and backfilled across the
existing 28 spec.md files. End-to-end value in a single slice: anyone
reading any spec.md sees a `status:` that matches reality, and the
status board regen keeps it that way going forward.

**DoR:**

- ✅ `iter_slices` (`skills/_common/parsing.py:174`) walks both
  spec.md-embedded sections and sibling `slice-*.md` files
  deterministically.
- ✅ `_slice_frontmatter` + `**STATUS:**` regex pattern already used
  in `collect_slices` is the canonical slice-status reader.
- ✅ `set_frontmatter_field` (`_common/parsing.py`) writes a single
  frontmatter field idempotently.
- ✅ `VALID_STATUSES` enumerates `DRAFT`, `IN_PROGRESS`, `DONE`,
  `DEFERRED`, etc. — the rollup output is a subset of this enum.
- ✅ Spec 030's spec.md states the rollup rule (Goal #4) and the
  defensive no-frontmatter behavior (Goal #6).

**Acceptance Criteria:**

1. **`compute_spec_status(spec_path: Path) -> str`** exists in
   `skills/spec-workflow/workflow.py` as a pure function. Returns
   one of `"DRAFT"`, `"IN_PROGRESS"`, `"DONE"`. The rule:
   - No slices at all (empty `iter_slices`) → `"DRAFT"`.
   - At least one non-DEFERRED slice AND every non-DEFERRED slice
     has status `DONE` → `"DONE"`.
   - All slices are DEFERRED, OR every non-DEFERRED slice has
     status `DRAFT` → `"DRAFT"`.
   - Anything else → `"IN_PROGRESS"`.

   Tested in isolation with synthetic spec dirs covering: empty,
   single-DRAFT, single-DONE, single-DEFERRED, all-DEFERRED,
   mixed-DONE-DRAFT, mixed-DONE-DEFERRED, mixed-IN_PROGRESS-DONE,
   legacy embedded sections, file-per-slice layout, and a mix of
   both.

2. **`workflow.py transition <spec.md> <slice> <new-status>`**
   computes the rollup after the slice write succeeds and updates
   spec.md's frontmatter `status:` field when (a) the spec.md has a
   frontmatter block, AND (b) the computed value differs from
   what's currently there. The transition's primary side-effect
   (slice mutation) is unchanged; rollup is an additional write
   ordered AFTER the slice write.

3. **`workflow.py status-board <project-dir>`** computes and
   writes the rollup for every spec it walks (one write per spec
   when the value would change; idempotent no-op otherwise). The
   rollup write happens regardless of whether the board's table
   text changed — a spec whose status flips from DRAFT → DONE
   updates spec.md even if the per-slice rows in the board are
   unchanged.

4. **No frontmatter → no write.** A spec.md without a frontmatter
   block at all (defensive case; none exist today) is left
   untouched by both write paths. No frontmatter insertion. The
   `compute_spec_status` function still returns its computed value
   (it doesn't *need* spec.md to be writable), but the write step
   is skipped silently.

5. **Backfill verification.** Running
   `python3 skills/spec-workflow/workflow.py status-board .` from
   the jig project root flips every fully-DONE spec from
   `status: DRAFT` to `status: DONE` in a single invocation. The
   slice's deviation log lists the before/after counts (expected:
   ~25 specs flip to DONE, ~3 remain DRAFT, ~0 become
   IN_PROGRESS today — exact numbers verified at implementation).

6. **Existing transition / status-board tests still pass.** No
   regression in the existing 16 workflow tests; new tests for
   `compute_spec_status`, the transition integration, and the
   status-board integration are additive.
