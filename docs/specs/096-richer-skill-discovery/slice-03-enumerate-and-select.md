## Slice 096-03 — enumerate-and-select

**Goal:** Absent config, jig picks up a richer skill with **zero configuration**:
Python enumerates candidate skills by category (recall-only), the orchestrator
selects one, and `review.py` takes that selection as an explicit argument and
hands the read-only reviewer the resolved path.

**Why `arch_review: true`:** introduces a new required CLI contract
(`--richer-skill`) across five pass recipes and moves a resolution
responsibility from Python into the orchestrator — a public-contract and
boundary change.

**DoR:**
- ✅ 096-02 DONE (name→path resolution + baseline exclusion exist).
- ✅ Spike evidence recorded: naive substring matching over-nominates
  (`morning-github`), so the nominator must not be trusted to pick.
- ⚠️ **Claude only.** The Codex selection path is gated on 096-04's spike
  (ADR-0039 OQ6); this slice ships Claude, and Codex continues on 096-01's
  config path until 096-04 resolves.

**Acceptance Criteria:**

1. **Enumeration nominates candidates by category — recall, not precision.**
   A helper enumerates all non-baseline skills across scopes and returns those
   plausibly matching a category, using description signal. It MAY over-offer;
   it MUST NOT be the thing that picks. Deterministic and order-stable for a
   given filesystem state.
2. **`--richer-skill <name|none>` is a required argument on all five passes.**
   `review.py pr-review …` (and the other four) refuse with a non-zero exit and
   a clear message when the flag is absent. Requiredness is load-bearing
   (ADR-0039): a silent default would decay this into spec 031's inert prose.
3. **A supplied name is validated deterministically before use.** The name is
   resolved via 096-02; the pass uses it only when it resolves to an existing,
   non-baseline SKILL.md. An unresolvable or baseline-marked name falls back to
   jig's baseline and does **not** error the pass (a bad pick must not block
   review) — but is recorded as such (096-05).
4. **`--richer-skill none` is honored and yields the baseline** without error.
   Explicitly supported: the user may legitimately want no richer skill applied.
5. **Precedence holds end-to-end.** Config (096-01) wins over any supplied
   selection; the supplied selection wins over the legacy exact-name lookup;
   baseline is last. `detect_richer_skill`'s exact-name/user-scope-only behavior
   is **removed** in this slice, superseded by the chain.
6. **The orchestrator is instructed to select, in the skill prose.**
   `spec-workflow` / `bug-fix` SKILL.md recipes tell the orchestrator to pick the
   single best candidate for the category and pass it — including the
   multiple-candidates rule (pick one, do not refuse) and the honest framing that
   the pick is a heuristic, overridable by config.

**Edge cases to cover explicitly:**
- Zero candidates enumerated → `none` is the correct selection; baseline applies.
- Multiple genuine candidates → orchestrator picks one; alternatives are carried
  forward for the 096-05 record. Enumeration itself never tiebreaks by lexical
  order (the spike showed that elevates a false positive).
- A supplied name matching a skill that exists but at a scope the reviewer
  cannot read → falls back to baseline, recorded.
- Non-interactive / CI invocation with no orchestrator → `--richer-skill none`
  is the documented value; config remains the CI-reproducible path.
