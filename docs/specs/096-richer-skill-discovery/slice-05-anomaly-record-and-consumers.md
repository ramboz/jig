## Slice 096-05 — anomaly-record-and-consumers

**Goal:** Make "a richer skill was available and was not applied" **visible**.
The evidence artifact records the applied skill *and* the candidate set the
orchestrator was shown, and at least one committed consumer surfaces the
unapplied-candidates anomaly — so the question "did deferral actually work?" is
answerable after the fact instead of being invisible.

**Why this exists:** every fallback path in the precedence chain converges on
jig's baseline, which is exactly the reported bug's terminal state. Requiredness
of `--richer-skill` enforces arity, not correctness. Auditability — not
enforcement — is what ADR-0039 can honestly offer, so it must actually be built
rather than deferred to "an implementation detail."

**DoR:**
- ✅ 096-03 DONE (selection + validation exist, so there is something to record).
- ✅ ADR-0014's evidence-artifact shape understood — this slice **extends** the
  frontmatter; it must **not** change the gate predicate.

**Acceptance Criteria:**

1. **The evidence artifact records skill + candidate set.** `record-review`
   writes the applied skill (or `none`) and the candidate set the orchestrator
   was **actually shown and declined**. Recording the choice alone is
   insufficient — it cannot distinguish "nothing installed" from "three
   installed, none applied."
2. **The anomaly is calibrated, not raw.** The anomaly fires only against the
   shown-and-declined set, never the raw nomination list. The recall-only
   nominator deliberately over-offers, so a naive definition would fire on
   nomination noise — on the probed corpus, a legitimate `none` would trip it via
   `morning-github`.
3. **The anomaly does NOT block.** `transition … REVIEWED` behaves identically
   with and without an anomaly present. ADR-0014's gate stays a one-line
   predicate on `verdict:`; a user who legitimately declines an installed skill
   must still reach REVIEWED. A test asserts this explicitly.
4. **At least one committed consumer surfaces it.** `check-reviews` emits a
   warning naming the declined candidates; `status-board` renders an aggregate
   count. Without a consumer the record is inert YAML and ADR-0039's
   most-likely-to-fire kill criterion becomes undetectable by construction.
5. **Backward compatibility.** Evidence artifacts written before this slice
   (no skill/candidate fields) parse without error and produce no anomaly —
   absence of data is not evidence of an anomaly.
6. **The known blind spot is documented, not papered over.** If enumeration
   nominates nothing, no anomaly fires and a recall failure is invisible. This
   is recorded in prose (spec + `docs/skill-routing-verification.md`) as an
   accepted gap whose mitigation is config precedence (096-01), not as a solved
   problem.

**Edge cases to cover explicitly:**
- Anomaly + `verdict: pass` → transition succeeds, warning emitted.
- Config-selected skill (096-01) → no anomaly, even when other candidates exist
  (the user chose deliberately).
- `--richer-skill none` with zero candidates → no anomaly (nothing was declined).
- Malformed / partial candidate data in an artifact → parsed defensively, no
  crash in `check-reviews` or `status-board`.
