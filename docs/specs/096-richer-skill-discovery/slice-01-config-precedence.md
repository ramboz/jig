## Slice 096-01 — config-precedence

**Goal:** A project can name its richer review skill per category in
`scaffold.json` (`review.<category>_skill`), and all five extensible review
passes read-and-apply that skill's SKILL.md instead of jig's baseline — closing
the reported bug deterministically, on both hosts, with no enumeration and no
marker.

**Why this slice is first:** it is the only resolution path ADR-0039 can
*guarantee*, and the destination every kill criterion falls back to. Shipping it
before the zero-config layer means a later abandonment degrades to a working
feature rather than a half-built one (ADR-0039 §6).

**DoR:**
- ✅ [ADR-0039](../../decisions/adr-0039-richer-skill-discovery.md) Accepted.
- ✅ `skills/_common/project_layout.py` exists as the precedent for reading a
  typed, validated block out of `scaffold.json` (spec 084 / ADR-0033).
- ✅ The five extensible passes exist in `review.py`: `build_pr_review_prompt`,
  `build_arch_review_prompt`, `build_code_health_review_prompt`,
  `build_design_review_prompt`, and the security pass surface.

**Acceptance Criteria:**

1. **A `review` block in `scaffold.json` resolves a skill by name or path.**
   A helper (sibling of `project_layout.docs_root`) reads
   `review.<category>_skill` for each of the five categories
   (`pr_review_skill`, `arch_review_skill`, `security_review_skill`,
   `code_health_skill`, `design_review_skill`). A bare name resolves against the
   known scopes; a path is used as-is. Absent block / absent key / empty string
   → `None` (jig's baseline), no error.
2. **Malformed config refuses loudly, not silently.** A non-object `review`, a
   non-string `<category>_skill`, or a configured name that resolves to no
   existing SKILL.md raises a typed error naming the offending key and value —
   it does NOT silently fall back to the baseline. Rationale: a config the user
   deliberately wrote and mistyped is the one case where silence reproduces the
   original bug with the user believing they fixed it.
3. **All five passes honor it.** With `pr_review_skill` configured, the craft
   pass prompt names that concrete path and instructs read-and-apply
   (superseding the inlined baseline buckets); likewise arch, security,
   code-health, and design with their own keys. Each still normalizes findings
   into the shared `VERDICT / REASONING / SPECIFIC ISSUES / RECONCILIATION
   NOTES` envelope.
4. **Config wins over the legacy exact-name lookup.** When both a configured
   skill and a `~/.claude/skills/<category>/` install are present, the configured
   one is used. (`detect_richer_skill`'s legacy behavior is retained as a
   fallback in this slice and is not yet removed — 096-03 supersedes it.)
5. **Host-portable.** Resolution reads only the filesystem + frontmatter; no
   router, no `Skill` tool, no Claude-only path. Codex-rendered SKILL.md prose
   describes the same mechanism with Codex scopes
   (`$HOME/.agents/skills`, `.agents/skills`, `/etc/codex/skills`).
6. **The configured skill is recorded.** `record-review` writes which skill was
   applied (or `none`) into the evidence artifact frontmatter. This is the
   minimum viable half of the ADR-0039 auditability requirement; the candidate
   set and the anomaly land in 096-05.

**Edge cases to cover explicitly:**
- `scaffold.json` absent entirely (jig's own repo) → `None`, no error.
- Configured skill exists but is unreadable (permissions) → typed error per AC2.
- Configured skill is jig's own baseline path → allowed (explicit user intent
  overrides the marker; the marker is a *discovery* filter, not a config filter).
- `docs_root = "."` projects — config discovery is sentinel-anchored the same way
  `project_layout` is, not docs-root-relative.
