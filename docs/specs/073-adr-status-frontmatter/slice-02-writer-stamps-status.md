## Slice 073-02 — writer stamps frontmatter status

**Goal:** Make `adr.py` write the canonical `status:` frontmatter field in
lockstep with the prose `## Status` line on `new` / `accept` / `supersede`,
and add `status: Proposed` to the ADR template — so new ADRs carry the
frontmatter status that 073-01's reader honors.

**DoR:**
- ✅ 073-01 DONE — the reader honors frontmatter `status:` and recognizes
  `Superseded`.
- ✅ `_common.parsing.set_frontmatter_field` available (already used by
  `adr.py` for `frame_review` / `last_verified`).

**Acceptance Criteria:**

1. **`new` stamps `status: Proposed`.** A freshly scaffolded ADR carries
   `status: Proposed` in frontmatter (alongside `frame_review: true`) **and**
   the prose `Proposed (date)` line. All existing `new` behavior is preserved;
   the field is added.
2. **`accept` sets `status: Accepted`.** `adr.py accept <NNNN>` sets
   frontmatter `status: Accepted` in the **same write** that flips the prose to
   `Accepted (date)`. After accept, frontmatter and prose agree.
3. **`supersede` sets `status: Superseded` on the old ADR.** `adr.py supersede
   <old> <new>` sets the old ADR's frontmatter `status: Superseded` in the
   **same write** that appends the prose `Superseded by …` line. The new ADR
   retains `status: Accepted`.
4. **Template carries the field.** `templates/docs/decisions/adr-0000-template.md`
   frontmatter includes `status: Proposed`.
5. **Synchronized-write lock (regression guard — ADR-0026 mandated).** A test
   asserts that after `supersede`, the old ADR's frontmatter `status:` is
   `Superseded` **and** its prose carries the `Superseded by` line — i.e. prose
   and frontmatter cannot diverge. Mirror the assertion for `accept`
   (frontmatter `Accepted` ⇔ prose `Accepted (date)`).
6. **End-to-end with the reader.** An ADR created → accepted → superseded
   resolves correctly through 073-01's `_lookup_adr_accepted` *from
   frontmatter*: satisfied after accept, not satisfied after supersede.
