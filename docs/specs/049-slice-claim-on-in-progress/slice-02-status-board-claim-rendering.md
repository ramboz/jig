## Slice 049-02 — status-board-claim-rendering

**Goal:** Teach `workflow.py status-board` to surface `claimed_by:`
for `IN_PROGRESS` rows so contributors can scan the board and see
which worktree owns each in-flight slice. Idempotent: no row churn
when claims are unchanged.

**DoR:**
- ✅ Slice 049-01 in production: `claimed_by:` is set/cleared by
  `transition` and reachable from frontmatter.
- ✅ Status-board regen race-detection (slice 028-03) protects the
  write surface.

**Acceptance Criteria:**

1. **`IN_PROGRESS` rows render the claim.** The status cell renders
   as `IN_PROGRESS (<claimed_by>)` when the slice has `claimed_by:`
   set; falls back to plain `IN_PROGRESS` when absent (legacy
   slices, slices claimed before this slice landed).
2. **Other states render unchanged.** `DRAFT`, `READY_FOR_REVIEW`,
   `READY_FOR_IMPLEMENTATION`, `REVIEWED`, `RECONCILED`, `DONE`,
   `DEFERRED` rows are byte-for-byte identical to the pre-049-02
   render.
3. **Idempotent regen.** Re-running `status-board` on an unchanged
   board produces no diff (existing 028-03 contract preserved).
4. **Notes column preserved.** Per the 028-03 / 030-02 contract,
   the Notes column survives regen. The claim suffix renders in the
   Status column, not Notes.
5. **Deferred-slices table unaffected.** DEFERRED rows live in a
   separate table per spec 015; they cannot have a claim and the
   helper does not add one.
6. **Truncation guard.** If `claimed_by:` exceeds 30 characters
   (e.g., long branch name), the suffix renders as
   `IN_PROGRESS (<first-27-chars>…)` to keep the cell width bounded.
   Pin the truncation length in a constant for easy adjustment.
7. **Fixture coverage.** Tests cover: rendered suffix when set,
   no suffix when absent, unchanged non-IN_PROGRESS rows, truncation
   above the bound, idempotent regen.

### Deviation log (after reconciliation)

The original spec is preserved above. Implementation notes:

1. **Rendering choice: suffix-in-Status-cell (open question resolved as
   planned).** The spec's open question (suffix vs. new column) was
   resolved in favor of the suffix — `render_status_table` renders
   `IN_PROGRESS (<claimed_by>)` in the existing Status cell, no new
   column, no schema churn. Mirrors the spike-marker precedent (029-02).

2. **Truncation pinned at 30/27 (open question resolved as planned).**
   `CLAIM_DISPLAY_MAX = 30` (render in full at or below) / `CLAIM_DISPLAY
   _TRUNC = 27` (else first-27 + ellipsis), matching AC6 verbatim, with a
   boundary test (exactly-30 not truncated) alongside the over-bound test.

3. **`claimed_by` threaded as a 6th `collect_slices` tuple element.**
   Backward-compatible: `render_status_table` / `render_deferred_table`
   read `row[5]` only under `len(row) >= 6` guards, so legacy 3/4/5-tuples
   still render (covered by `test_legacy_5tuple_row_renders_plain`).

4. **Reviewer nits folded back in (both passes pass).** (a) Extended the
   `render_status_table` docstring to list the 6-tuple shape (parity with
   the updated `collect_slices` docstring). (b) Added an invariant comment
   tying `CLAIM_DISPLAY_TRUNC < CLAIM_DISPLAY_MAX`. The "`|` in
   `claimed_by` corrupts the table" question was considered and dismissed
   as non-realistic (git refs disallow `|`; `JIG_CLAIM_ID` is operator-
   controlled) and consistent with the file's existing unescaped-cell
   posture — recorded here so it isn't re-litigated.

5. **Self-dogfood.** While IN_PROGRESS, 049-02's own board row rendered
   `IN_PROGRESS (claude/competent-banach-f69ece)` on regen — the visible
   "who owns this" view this slice ships, observed on its own row.

6. **Docs updated:** the `spec-workflow` Skills-table row in `CLAUDE.md`
   now mentions the claim-on-IN_PROGRESS contract; the spec 049 Active-
   specs entry was compressed on close-out; status board regenerated.
