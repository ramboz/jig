## Slice 027-01 — post-edit-verify-hook

**Goal:** Ship a `PostToolUse` hook on `Edit|Write|MultiEdit` that
performs a mechanical "did the claimed write actually land in the
file" check and emits a soft warning on mismatch. No semantic
verification, no auto-retry — just a same-turn signal that the agent
or user can act on before the context dissolves.

**DoR:**
- ✅ Spec 026 (context-fill telemetry) can ship before or after this
  slice — they are independent.

**Acceptance Criteria:**

1. **New hook script** at `hooks/scripts/jig-post-edit-verify.sh`
   (Python 3 inline body, parallels existing five scripts in shape).
   Registered as `PostToolUse` with matcher `Edit|Write|MultiEdit`
   in `hooks/hooks.json`.
2. **Edit verification.** For tool `Edit`, the hook reads `file_path`
   and verifies `new_string` is present in the post-edit file content.
   If `new_string` is empty (deletion), verifies `old_string` is no
   longer present.
3. **Write verification.** For tool `Write`, the hook reads
   `file_path` and verifies the first 200 bytes match the requested
   `content`'s first 200 bytes (cheap sanity check, not full
   re-read).
4. **MultiEdit verification.** For tool `MultiEdit`, the hook walks
   each edit in the array and applies the AC #2 rule to each.
5. **Soft warning on mismatch.** On any failed check, the hook emits
   `{"continue": true, "additionalContext": "<file> post-edit check
   failed: <substring> not found. Re-read and retry."}`. Never sets
   `continue: false`.
6. **Opt-out via `JIG_POST_EDIT_VERIFY=0`.** When set, hook exits 0
   immediately with no output. Tests cover both states.
7. **Bounded read.** Hook never reads more than 64KB from any file.
   For files larger than 64KB, the read targets the byte range
   surrounding the edit (or first 64KB for Write). A test pins this
   bound.
8. **Robust to missing file.** If `file_path` doesn't exist after
   the tool call (which shouldn't happen but might in edge cases),
   the hook exits 0 silently — never blocks the agent on
   environmental weirdness.

### Deviation log (after reconciliation)

The original spec is preserved above. Implementation notes:

1. **AC #7 implementation-narrowing.** AC #7's first sentence
   ("Hook never reads more than 64KB from any file") is honored
   verbatim — the implementation uses a single `f.read(65536)`
   capped read. AC #7's second sentence — "For files larger than
   64KB, the read targets the byte range surrounding the edit (or
   first 64KB for Write)" — was **narrowed at implementation time
   to head-only (first 64KB) for Edit and MultiEdit as well**.
   Reason: the `tool_input` payload for Edit/MultiEdit doesn't
   carry a byte offset that the hook could use to target the
   edit region; the only path to "surrounding the edit" would be
   to search for `old_string`, but `old_string` has already been
   replaced post-edit. Effect: for files >64KB with an edit past
   the head, the hook silently exits with no warning (best-effort
   bailout), which is documented in the script's `check_edit`
   inline comment and pinned by
   `test_10mb_file_with_edit_beyond_64kb_exits_silently` in
   `scripts/test_post_edit_verify.py`. The asymmetric "Write
   reads first 64KB" half of AC #7's second sentence remains
   verbatim. This is a planned narrowing of an aspirational AC
   clause; future enhancement could substring-anchor by
   streaming.

2. **MultiEdit verification trade-off.** AC #4 says "the hook
   walks each edit in the array and applies the AC #2 rule to
   each." Implementation does so literally: each edit's
   `new_string` is searched in the *single* post-edit file
   content. If edit #2 overwrites edit #1's `new_string`
   (chained transforms), the check on edit #1 will false-positive
   warn. This matches the spec's "Open questions" entry on race
   tolerance ("tolerate (best-effort) or warn (false-positive
   risk)") — implementer chose "warn" because (a) false-positives
   surface in the same turn and are cheap for the agent to
   dismiss, and (b) silent-pass on a missing earlier edit risks
   the exact stale-claim failure mode the spec exists to catch.

3. **Hook timeout: 5s, not the spec's "~2 seconds".** The spec's
   "Goals" §6 ("Bounded cost… times out at ~2 seconds") was
   set as a soft target. Implementation registers the hook with
   `timeout: 5` in `hooks/hooks.json` to mirror every sibling
   script's timeout — keeping uniformity for the operator's
   mental model. The 64KB read budget plus the no-network /
   no-fork shape mean wall-clock time stays well under 2s in
   practice; the 5s registered timeout is generous slack.

4. **Scaffold-mode parity work folded into the same slice.** AC
   #1 names hook-script creation + `hooks/hooks.json`
   registration only. The deliverable also threads the new hook
   through `scripts/verify_install.py` (`_EXPECTED_HOOK_SCRIPTS`)
   and `skills/scaffold-init/test_scaffold_mode.py`
   (`EXPECTED_HOOK_SCRIPTS` + `EXPECTED_HOOK_EVENTS` += new
   `PostToolUse`) so scaffold-mode installs the new hook on
   downstream projects. This is required for the scaffold-mode
   parity ADR-0006 contract and is not a separate slice. Two
   stale "five" docstrings (`verify_install.py:181/191`,
   `test_scaffold_mode.py:362-363`) were swept in the same
   change after the compliance reviewer flagged them — itself an
   instance of the staleness anti-pattern this slice exists to
   catch.

5. **Doc updates folded in.** `docs/architecture.md` (mermaid
   diagram + hook-spine summary), `README.md` (hook-count
   sentence), and `docs/memory/glossary.md` ("five jig hooks"
   blurb) were updated to reflect the new six-hook surface.
   These are user-visible counts the deviation-log catalog the
   spec cites (012-01 stale labels, 016-01 stale `014-` sweep,
   017 catalog, 022-02 stale SKILL.md prose) all warn about; the
   updates land in the same slice to avoid the spec's
   self-described pattern.
