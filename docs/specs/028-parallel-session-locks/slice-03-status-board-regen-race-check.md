## Slice 028-03 — status-board-regen-race-check

**Goal:** `workflow.py status-board` refuses to overwrite
`docs/specs/README.md` if the on-disk file has changed since the
regen started (another worktree regen'd in the gap). On detection,
surface a clear re-run instruction.

**DoR:**
- ✅ `workflow.py status-board` exists and is the canonical writer
  of `docs/specs/README.md`.

**Acceptance Criteria:**

1. **Pre-regen checksum.** `status-board` captures the checksum (or
   mtime + size) of the existing `docs/specs/README.md` before
   reading any spec frontmatter.
2. **Pre-write check.** Before writing the regenerated board, the
   helper re-checksums the file and refuses to write if it changed.
3. **Refusal message.** On refusal, prints "status board changed
   during regen — another writer may have run. Re-run
   `workflow.py status-board` to retry." Exits non-zero (suggested
   exit code 4, after 0/1/2/3 conventions).
4. **`--force` escape.** A `--force` flag bypasses the check and
   writes anyway. Documented in helper docstring + SKILL.md.
5. **Tests cover all three branches.** No-race (default behavior
   unchanged), detected-race (refusal + exit 4), forced-overwrite
   (`--force` writes despite checksum mismatch). Use a temp
   directory + manual file mutation between the pre-check and the
   write to simulate the race.
6. **Curate-Notes preservation unchanged.** The status-board
   header documents Notes-column preservation across regen; this
   slice changes nothing about that. A regression test pins it.

### Deviation log (after reconciliation)

**§1 — Checksum strategy: SHA256 on read bytes (not mtime+size).**
mtime resolution varies by filesystem (some macOS volumes still
expose 1-second granularity), and "size unchanged but content
changed" cases (e.g. swap one Notes value for another of equal
length) would slip past a size-only check. SHA256 on a few-KB
README is cheap (sub-millisecond) and content-exact, so the
race-detection guard is bulletproof to filesystem timing quirks.
The helper is extracted to module scope as `_checksum(path)` so
tests can `unittest.mock.patch.object(wf, "_checksum")` to inject
deterministic mid-regen mutations.

**§2 — Exit code 4 via `StatusBoardRaceError(WorkflowError)`.**
Per AC #3. The new exception subclass is caught in `main()` before
the generic `WorkflowError` handler so the subclass routes to its
dedicated exit code (4) rather than the parent's exit code (2).
Exception ordering matters: `except StatusBoardRaceError` MUST
appear before `except WorkflowError` because Python's exception
matching is first-match-wins, not most-specific-wins. Exit code 4
is the next free after 0 (success) / 1 (programming error) / 2
(WorkflowError refusal) / 3 (used by scaffold.py + migrate.py for
config-conflict + unmanaged-hooks).

**§3 — Race-check positioning: AFTER the idempotent fast path.**
The existing fast path at `if new_content == existing: return
"already current"` runs first. This means:
(a) A regen with no actual changes skips both the post-checksum
    read and the write — no race possible, no wasted I/O.
(b) `--force=True` combined with an idempotent state still returns
    "already current" rather than unconditionally writing. The
    craft-pass reviewer flagged this as a coverage gap; added
    `test_force_respects_idempotent_fast_path` to pin the
    behavior against future refactors.

**§4 — `--force` skips BOTH pre- and post-checksum reads.** When
`force=True`, the pre-regen checksum capture is short-circuited
(`pre_checksum = None if force else _checksum(board_path)`), so
there's no wasted I/O on a forced overwrite. The forced path is
intentionally minimal: it's a "trust the operator" escape hatch
for cases where the race-detection guard is in the way (e.g.
intentional overwrite after manual conflict resolution).

**§5 — Stale-checksum false-positive: identical-content rewrites
do NOT trigger a race.** If another writer rewrites README.md
with byte-identical content, SHA256 stays the same → no race
detected → write proceeds. This is the correct behavior for a
content-based check: "same content" means "no observable race."
A test (`test_identical_content_rewrite_does_not_trigger_race`)
pins this. Documented in code comments + SKILL.md so future
readers don't mistake it for a bug.

**§6 — Spec-rollup writes (`_write_spec_rollup`) are intentionally
outside the race-check window.** Those writes touch individual
`docs/specs/*/spec.md` files (not the README), and they happen
between the pre-checksum and the README write. The race-check
guards only the README. Two reasons: (a) spec-rollup writes are
idempotent per-spec and don't conflict with another worktree's
rollup, (b) widening the guard to cover individual spec files
would require per-spec checksums and N round-trips — overkill
for the current failure mode. If a future incident shows spec.md
rollup conflicts in practice, revisit.

**§7 — Residual TOCTOU window acknowledged.** Between the
post-checksum read on the line immediately above
`board_path.write_text(...)` and the write itself, there's a
microscopic window where another writer could slip in. This is
inherent to any check-then-write pattern without filesystem-level
atomicity. The guard is "best-effort detection," not "atomic
write." The slice's framing accepts this: the goal is to catch
the empirical case (two worktrees regenerating seconds apart),
not to provide hard atomicity. A future slice could close the
residual window with `os.rename` of a tempfile + an atomic-CAS
shim, but the cost-benefit doesn't justify it today.

**§8 — AC #3 refusal message pinned by `assertEqual`, not
`assertIn`.** The test uses character-exact equality on the
refusal message: a future "improvement" to the wording (e.g.
adding a hint or changing punctuation) will fail loudly. AC #3
named the exact wording; pinning it strictly enforces the
contract.

**§9 — Craft-pass coverage gap closed.** Craft reviewer noted no
explicit test for `--force` + idempotent-fast-path interaction
(the code is correct by statement ordering but unprotected
against a future refactor). Added
`test_force_respects_idempotent_fast_path` (9 tests total in
`StatusBoardRaceCheckTests`).

**§10 — Duplicate `--force` test bodies acknowledged, not
refactored.** Craft reviewer flagged that
`test_force_python_api_bypasses_race_check` and
`test_force_cli_flag_bypasses_race_check` have near-identical
bodies. Kept as separate tests rather than parametrized via
`subTest` because the AC explicitly calls out both the Python
API path AND the CLI flag path — having two grep-able test
methods makes the AC coverage explicit. Trading a tiny amount of
duplication for naming clarity.

**§11 — Test ergonomics: importlib loader reused from slice
028-02 pattern.** `_import_workflow_module()` mirrors slice
028-02's `_import_memory_module()` shape, so tests can
monkeypatch module-scoped helpers (`_checksum`) without going
through the CLI subprocess. Faster test execution + cleaner
assertions.
