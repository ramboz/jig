## Slice 028-02 — inbox-and-refinement-todo-append-lock

**Goal:** Add an append-lock pattern (file-lock or reserve-on-main,
to be decided in implementation) to the helpers that append to
`docs/inbox.md` and `docs/refinement-todo.md`. Concurrent appends
from two worktrees never lose content.

**DoR:**
- ✅ Slice 028-01 DONE so the reserve-on-main pattern is generalized
  for use here if file-lock turns out insufficient.
- ✅ A helper exists (or is created in this slice) that appends to
  inbox / refinement-todo. Today these are hand-edited via the Edit
  tool; this slice may need to introduce a thin write helper as a
  prerequisite (TBD during implementation).

**Acceptance Criteria:**

1. **File-lock or reserve-on-main pattern picked.** Decision recorded
   in deviation log §1 with one-paragraph rationale. Lean: file-lock
   for shared-filesystem worktrees (the common case); reserve-on-main
   if the lock turns out to be insufficient under multi-host
   scenarios.
2. **Inbox helper.** A `<helper>.py append-inbox <text>` (path TBD;
   may live in `_common` or in a new `inbox.py`) acquires the lock,
   appends the text with timestamp, releases. Two concurrent
   invocations serialize cleanly; neither loses content.
3. **Refinement-todo helper.** Same shape, same lock surface, same
   semantics.
4. **Lock timeout.** A waiting writer that doesn't acquire within
   N seconds (default 5) exits with a clear error. No silent hangs.
5. **Stale-lock recovery.** If the lock file is held by a non-running
   PID (crashed writer), the helper detects and reclaims it. Edge
   case: PID reuse — document the small window in the helper
   docstring.
6. **Tests cover contention.** Use threading or subprocess to
   simulate two concurrent appends and assert both land. (Don't use
   real `time.sleep` to manufacture races — use the `_SubprocessRecorder`
   pattern + deterministic ordering.)

### Deviation log (after reconciliation)

**§1 — Pattern picked: file-lock (not reserve-on-main).** AC #1
required a recorded decision with one-paragraph rationale.
Inbox/refinement-todo appends are low-rate (a handful per session at
most). Reserve-on-main would pay a network round-trip per write and
require origin-main to be a writable target — overkill for an append
surface where the empirical collision case is multiple worktrees on a
single machine. File-lock (specifically `fcntl.flock`) is the cheaper
fit. Multi-host writes against a shared inbox.md are explicitly out of
scope per spec 028 Goals #1 and Open questions §1, so file-lock is
sufficient. If a future failure mode shows up across hosts, the
extension path is to layer reserve-on-main on top — same approach
slice 028-01 ships for ADR numbering.

**§2 — `fcntl.flock`, not PID-file polling.** Kernel auto-releases the
lock on process exit (crash, kill, normal exit), so AC #5's stale-lock-
recovery requirement is trivially satisfied. There is no PID-reuse
window: the kernel — not the PID file — is the source of truth. The
holder PID is still written into the lock file, but as a *diagnostic*
(so an inspecting user can see who's blocking), not as the held-bit.
This eliminates an entire class of races that a PID-polling
implementation would have to handle (was-running-but-now-isn't,
PID-recycled-by-the-kernel, etc.).

**§3 — Lock surface: `<git-common-dir>/jig-locks/<artifact>.lock`.**
Resolved via `git rev-parse --git-common-dir` from the target as cwd.
This is critical: multiple worktrees of the same project share a single
`.git/` directory, so the common-dir is the only filesystem location
that serializes writes across worktrees. A naive `<target>/.jig/locks/`
path would only serialize within one worktree — wrong scope. Outside a
git repo (e.g., un-scaffolded directory) the helper falls back to
`<target>/.jig/locks/` so the helper still works on bare projects.
`.git/jig-locks/` is naturally outside git tracking (the `.git/`
directory is not committed), so the lock files never get accidentally
committed or merged.

**§4 — Helpers inline in `skills/memory-sync/memory.py`.** Per ADR-0002's
"three-callers triggers extraction" rule (and the precedent set by
slice 028-01's inline-mirror decision), the lock primitive (`_file_lock`),
the dir resolver (`_resolve_lock_dir`), and the new `add_refinement_todo`
function all live inline in `memory.py`. Two callers (add_inbox,
add_refinement_todo); extraction defers until slice 028-03 (or any
third caller) needs them. The block is bracketed by
`# ---------- Slice 028-02: file-lock for inbox + refinement-todo appends ----------` /
`# ---------- end slice 028-02 ----------` markers naming exactly which
helpers are slice-028-02 artifacts. When extraction fires, this block
is the candidate.

**§5 — `add-refinement-todo` takes raw text (no structured flags).**
The caller composes the markdown chunk (H2 category, deferred-/
resolution-trigger structure, etc.); the helper just appends with a
boundary-newline guarantee and the file lock. This mirrors
`add-inbox`'s "caller picks the format" shape (per AC #3: "same shape,
same lock surface, same semantics"). The hand-edited H2-categorization
of refinement-todo.md is preserved as a hand-edited concern; the
helper makes no attempt to place the new entry under an existing
category. If a future need surfaces, structured flags can land in a
later slice without breaking this surface.

**§6 — Polling cadence is 50ms.** `fcntl.flock` with `LOCK_NB` returns
immediately if the lock is held; the helper loops with a
`time.monotonic()` deadline and `time.sleep(0.05)` between attempts.
This is polling cadence, not race manufacture: 50ms is the worst-case
acquisition latency once the holder releases, which is fast enough
that no human notices, and slow enough that the polling overhead is
negligible. The deadline check happens before each `time.sleep` so the
helper exits within the configured timeout regardless of the last
poll's timing.

**§7 — Lock file persists on disk after release.** Creating-and-removing
a lock file races itself ("is this file fresh or a leftover?"); leaving
it persistent and using `fcntl.flock` as the held-bit sidesteps the
question. The file is small (just a PID) and lives under `.git/`,
which is not committed. No cleanup needed.

**§8 — CLI default timeout is 5s; Python API takes a kwarg.** AC #4
required a configurable timeout. The CLI default (`CLI_DEFAULT_LOCK_TIMEOUT
= 5.0`) is what users see; tests pass `timeout=0.2` directly to the
Python API to keep the contention-timeout test fast. No CLI flag was
added — adding one would expand the surface for marginal gain (the
test path is the only one that benefits from a different timeout).

**§9 — LockTimeoutError surfaces via the existing CLI catch-all.** The
existing `except Exception` block in `main()` formats `LockTimeoutError`
as `memory-sync failed: <message>` and exits 1. The error message
includes the lock path and the timeout, satisfying AC #4's "clear
error. No silent hangs." A dedicated handler was considered but the
existing path delivers the requirement; adding a specific handler
would be duplicate-without-benefit.

**§10 — Test ergonomics: importlib loader added.** Following slice
028-01's pattern, the new test class loads `memory.py` as a module via
`importlib.util.spec_from_file_location` so tests can call
`_file_lock` and pass `timeout=` to `add_inbox` directly (the CLI
doesn't expose a timeout flag — see §8). This keeps the contention
test fast (0.2s timeout) without adding CLI surface. The same loader
is also used by the lock-dir-resolution tests so they can exercise
`_resolve_lock_dir` without spawning subprocesses.

**§11 — `_refinement_todo_path` mirrors `_inbox_path`.** The
self-healing pattern (template file gets created if absent) was
already established by `_inbox_path`, `_glossary_path`,
`_learnings_path`. `_refinement_todo_path` follows the same shape:
default content is `"# Refinement Todo\n\n> Status: Draft (self-healed
by memory-sync)\n\n"`. This means the helper works on un-scaffolded
projects, same as add-inbox today.

No new deferred decisions surfaced during implementation; nothing
needed to be added to `docs/refinement-todo.md`.

**§12 — Compliance-pass fix: self-heal moved inside the lock.** The
first compliance reviewer flagged that `_inbox_path` and
`_refinement_todo_path` (both of which delegate to `_ensure_file`,
whose `exists()` → `write_text(default)` pair is TOCTOU-racy) were
being called *outside* `_file_lock`. Concurrent first-writes against
a non-existent inbox/refinement-todo could let writer-2's
`write_text(default)` clobber writer-1's already-appended bullet. The
window is microscopically small in practice (subprocess startup
dwarfs the `exists()`/`write_text` gap), but the slice's
"concurrent appends never lose content" goal is technically violated.
Fix: moved both self-heal calls *inside* the `with _file_lock` block.
Added `AppendLockFirstWriteRaceTests` (2 tests) that exercise
concurrent first-writes against a non-existent file (setUp does
`git init` only, NOT `scaffold()`, so neither artifact pre-exists).
Both regression tests pass. Full test suite remains green at 1197
tests.

**§13 — Craft-pass nits addressed.** The second-pass craft reviewer
returned PASS with five `[nit]` items, all addressed pre-transition:

- `subprocess.run` for `git rev-parse --git-common-dir` now passes
  `stderr=subprocess.DEVNULL`, so a non-git target no longer leaks
  `fatal: not a git repository` onto the calling process's stderr.
- `_resolve_lock_dir`'s exception handler widened from `except
  FileNotFoundError` to `except (FileNotFoundError, OSError)`. The
  original catch only covered the "git binary missing" case; the
  wider catch also covers `subprocess.SubprocessError`/permission-
  denied invocation paths.
- Removed the duplicate `lock_path.parent.mkdir(...)` at the top of
  `_file_lock`. `_resolve_lock_dir` already creates the parent;
  the second call was harmless but redundant.
- `test_lock_timeout_cli_default_5s_is_configurable` now asserts
  `memory.CLI_DEFAULT_LOCK_TIMEOUT == 5.0`. The original test only
  exercised the kwarg path; the name promised "pin the default" but
  didn't actually pin it.
- Moved `importlib.util` / `threading` / `time` imports from the
  mid-file slice marker to the top of `test_memory.py` per PEP 8.

**§14 — `add_inbox` vs `add_refinement_todo` newline-handling
asymmetry.** Craft-pass reviewer reconciliation note: `add_inbox`
uses plain `open(..., "a")` (the dated bullet always ends with `\n`),
whereas `add_refinement_todo` reads existing content under the lock
to check the trailing-newline boundary before writing (the
caller-composed chunk may or may not end with `\n`). The asymmetry
is intentional — inbox bullets have a fixed format with a guaranteed
trailing newline; refinement-todo entries are caller-composed and
need the boundary-insurance — but it wasn't called out in §5. Noting
it here so future readers see why the two helpers diverge.
