## Slice 028-02 — inbox-and-refinement-todo-append-lock

**Goal:** Add an append-lock pattern (file-lock or reserve-on-main,
to be decided in implementation) to the helpers that append to
`docs/inbox.md` and `docs/refinement-todo.md`. Concurrent appends
from two worktrees never lose content.

**DoR:**
- ✅ Slice 028-01 DONE so the reserve-on-main pattern is generalized
  for use here if file-lock turns out insufficient.
- ✅ A helper exists (or is created in this slice) that appends to
  inbox / refinement-todo. Today these are hand-edited via the Edit
  tool; this slice may need to introduce a thin write helper as a
  prerequisite (TBD during implementation).

**Acceptance Criteria:**

1. **File-lock or reserve-on-main pattern picked.** Decision recorded
   in deviation log §1 with one-paragraph rationale. Lean: file-lock
   for shared-filesystem worktrees (the common case); reserve-on-main
   if the lock turns out to be insufficient under multi-host
   scenarios.
2. **Inbox helper.** A `<helper>.py append-inbox <text>` (path TBD;
   may live in `_common` or in a new `inbox.py`) acquires the lock,
   appends the text with timestamp, releases. Two concurrent
   invocations serialize cleanly; neither loses content.
3. **Refinement-todo helper.** Same shape, same lock surface, same
   semantics.
4. **Lock timeout.** A waiting writer that doesn't acquire within
   N seconds (default 5) exits with a clear error. No silent hangs.
5. **Stale-lock recovery.** If the lock file is held by a non-running
   PID (crashed writer), the helper detects and reclaims it. Edge
   case: PID reuse — document the small window in the helper
   docstring.
6. **Tests cover contention.** Use threading or subprocess to
   simulate two concurrent appends and assert both land. (Don't use
   real `time.sleep` to manufacture races — use the `_SubprocessRecorder`
   pattern + deterministic ordering.)

**DoD:**
