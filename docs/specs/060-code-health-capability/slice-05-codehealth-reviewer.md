## Slice 060-05 — Distinct code-health reviewer pass

**Goal:** Add a dedicated **code-health review pass** to the post-implementation flow (alongside compliance / craft / arch), per ADR-0017 OQ4. `review.py` builds a code-health-review prompt; a read-only `reviewer` subagent consumes `health.py`'s *summary* (run by the spine, not the subagent) and renders the judgment a tool can't — e.g. is this duplication within the [ADR-0002](../../decisions/adr-0002-extract-helper-on-third-caller.md) mirror budget, is this complexity inherent or fixable.

**DoR:**
- ✅ 060-01 DONE (runner produces a normalized summary).
- ✅ 060-04 DONE (duplication summary available to judge).
- ✅ The always-on-vs-gated decision made (see AC3).

**Acceptance Criteria:**

1. **`review.py code-health` builds the pass prompt** (mirrors `review.py pr-review` / `arch-review`), feeding the reviewer the spec + deliverable + the `health.py` summary and returning the standard `VERDICT / REASONING / SPECIFIC ISSUES / RECONCILIATION NOTES` envelope with `[blocker]` / `[nit]` / `[strength]` tags.
2. **Spine runs the tool; the reviewer judges the summary.** Because the reviewer subagent is read-only (Read / Glob / Grep, no Bash), `health.py` is executed by the orchestrator / CI and its tight summary is passed *into* the prompt — never raw logs, never run by the subagent.
3. **Gating mirrors craft/arch, and the trigger is decided.** `[blocker]` entries block the `REVIEWED` transition; `[nit]` entries become reconciliation-log items. Whether the pass runs always or is gated by a slice frontmatter flag (the way `arch_review: true` gates the arch pass) is decided and documented in `SKILL.md`.
4. **Wired into the post-implementation flow** in `skills/spec-workflow/SKILL.md` as a defined pass with its own `record-review` evidence file (`reviews/slice-NN-code-health.md`), consistent with the ADR-0014 evidence gate.

### Deviation log (after reconciliation)

- **Gating decision: the code-health pass is GATED, not always-on.** It runs
  only when a slice's frontmatter declares `code_health_review: true`,
  mirroring `arch_review: true` exactly. Rationale (ADR-0017 "Becomes harder"
  + specs 055/057 context-cost discipline): the pass adds per-slice review
  cost (orchestrator turns + a subagent), so ADR-0017 advises gating it like
  arch-review rather than spending it on every slice. **Back-compat:** the
  flag defaults false everywhere — `required_passes(... code_health_review=False)`,
  `_code_health_review_flag` conservative-False on any miss,
  `slice_needs_code_health_review` False on any miss — so every existing
  slice (no flag) is unaffected. The full 2291-test suite stayed green.

- **`required_passes` signature change.** Added a keyword-only
  `code_health_review: bool = False` after the existing `arch_review`. All
  existing callers pass `arch_review=...` positionally-by-keyword and are
  unaffected by the default. `validate_evidence` now reads both flags and
  threads them in. `PASSES` grew a fifth member `"code-health"` (inserted
  before `reconciliation`), so `evidence_path`, `record-review`'s `--pass`
  choices, and `check-reviews` pick it up automatically (no extra wiring).

- **Summary-injection mechanism: `--summary-file PATH` with stdin fallback.**
  The `review.py code-health` subcommand reuses the existing `_read_summary`
  helper (the same one `record-review` uses) — `--summary-file` if given,
  else stdin. The read-only reviewer never runs `health.py`; the orchestrator
  runs it and feeds the tight summary IN (AC2). When no summary is provided
  the prompt degrades to a clear "(no health.py summary provided …)" note
  rather than crashing.

- **`detect_richer_skill` deliberately NOT wired.** Unlike pr-review /
  arch-review, the code-health prompt inlines jig's rubric and does not probe
  for a `~/.claude/skills/code-health/` user skill. Rationale: there is no
  established "richer code-health reviewer" skill category to defer to (the
  brief explicitly left this to my call). If such a category emerges, adding
  the deferral is a one-line `detect_richer_skill("code-health")` mirror.

- **Added `code-health-review-needed` CLI subcommand** to `workflow.py`
  (parity with `arch-review-needed`) so the SKILL.md bash recipe can shell
  out the gate query the same way. Not strictly required by the ACs, but it
  keeps the orchestration recipe symmetric with the arch pass.

- **Nothing deferred** to `docs/refinement-todo.md` — no real decision was
  punted during implementation.

**Reconciliation-time fixes (from the craft review's nits):**

- Fixed a backwards cross-reference in `skills/code-health/SKILL.md` ("see
  'The code-health review pass' below" → "above").
- Added two tests for the AC2 graceful-degrade paths the original suite left
  unasserted: `test_empty_summary_degrades_gracefully` (empty stdin → the
  prompt still builds and emits the "no health.py summary" note, exit 0) and
  `test_missing_summary_file_errors` (`--summary-file` at a nonexistent path →
  clean exit-2 `ReviewError`, no traceback).
- **"OQ4" is shorthand, noted.** The slice goal/DoR text references
  "ADR-0017 OQ4 (always-vs-gated)". ADR-0017's single *listed* Open Question
  is tier placement; the always-vs-gated reviewer choice is one of its
  "Settled specifics … left to the spec" forks. The gating decision is
  resolved here (deviation log + SKILL.md), NOT by editing the closed Accepted
  ADR (per ADR-0010). The "OQ4" label is loose shorthand with no functional
  inconsistency.
- **Field-name wrapper near-duplication (acknowledged, within budget).**
  `_code_health_review_flag`/`slice_needs_code_health_review` mirror their
  `arch_review` twins, differing only by the frontmatter field-name literal;
  the load-bearing truthiness already routes through the shared
  `frontmatter_flag_truthy`. Acceptable per ADR-0002 (preserves arch symmetry);
  a *third* such flag would cross the rule-of-three for the wrapper shape and
  warrant a `field_name`-parameterized helper.

## Amendments

- **2026-07-30 — bug 017: the stdin fallback became an explicit
  `--summary-file -`.** This slice's summary-injection mechanism was
  "`--summary-file PATH`, else stdin", implemented by sharing `_read_summary`
  with `record-review`. That shared fallback read stdin whenever it was not a
  terminal, using `isatty()` as a stand-in for "input is waiting" — a property
  it does not report — so a pipe whose write end nobody closed blocked
  forever. See [bug 017](../../bugs/017-record-review-blocks-on-stdin.md).

  Injection by pipe is unchanged in capability but now has to be asked for:
  `review.py code-health … --summary-file -`. Omitting `--summary-file`
  entirely keeps this slice's AC2 graceful degrade (empty summary → the
  "(no health.py summary …)" note, exit 0); only the *implicit* stdin read is
  gone. `record-review` diverges here: it now requires a body outright.
  `test_summary_read_from_stdin_when_no_file` was renamed
  `test_summary_read_from_stdin_when_requested` and passes the flag.
