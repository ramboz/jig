- [2026-05-12] Security-lens integration with `adobe-security-suite` (graceful degradation pattern). Adobe IT/Security distributes a Claude Code plugin (`adobe-security-suite` v1.6.1, 7 skills: foundations / services / client / cloud / lang / audit / antipatterns, sourced from the public `adobe-cursor-rules` repo and already shaped as a proper plugin with auto-invoking SKILL.md frontmatter). Sibling-install works out of the box — the auto-triggering skills fire on code writes alongside jig with zero coordination. Question is whether jig's reviewer should become *aware* of it so the verdict surface is consistent across projects that have it vs. don't. Proposed shape: a `security_lens: "adobe" | "builtin" | "off"` field in `scaffold.json` (default `"builtin"`); `review.py` reads the flag and either (a) appends a hand-off block to the reviewer prompt naming the Adobe skills to apply, or (b) embeds a tight built-in checklist (~10 always-applicable rules: hardcoded credentials, banned crypto, disabled security controls like `verify=False`, unvalidated sinks in new entry points — i.e. Adobe foundations' "Rule A/B/C" essentials, no more). Detection via `scaffold.json` not filesystem probing of `~/.claude/plugins/` — plugin install paths are fragile across marketplace / user / project scopes. Tradeoff: the builtin fallback *will drift* from Adobe's guidance over time, and projects on the two paths will get materially different findings; accepting that bounded divergence by keeping the fallback intentionally shallow ("Adobe gives depth; builtin gives a floor"). Relationship to other inbox items: this is one concrete answer to the multi-persona reviewer question above (option (c) — lens parameter), specifically for the Security persona. If the multi-persona spec lands as separate `/jig:arch-review` + `/jig:pr-review` skills (option (a)), the same `security_lens` flag plugs into `/jig:pr-review` instead. Explicitly NOT in scope: forking the `.mdc` rule files, bundling Adobe skills inside jig's manifest, or adopting Adobe's enterprise `settings.json` profiles (orthogonal workstation-policy decision).
